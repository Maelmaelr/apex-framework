# /apex v1.0

Apex is the main orchestrator in the main session.

For a lighter, easier-to-read summary of steps, skill/agent/script used, and routing conditions, see `apex-core-overview.md`.

## Effort levels (cross-cutting)

- Step 3 (hypothesis): emits `complexity_hint: low|medium|high` - heuristic estimate from prompt signals (verb scope, file / module names mentioned, abstraction-level keywords). Refined nowhere; consumed as-is by p2.0b.
- Step 6.c (screeners): high effort by default (classification quality matters; cost amortised across parallel shards).
- p2.0b (planner): per-teammate effort decided from `complexity_hint` + scope size; high-effort keyword fires when `complexity_hint == high`.

## Conventions

- **Standard safety paths** (always allowed in any scope artifact): `.claude-tmp/`, `~/.claude/tmp/`, `/tmp/{session}-*`, project `docs/**`, and any `README*` file at any depth (so `documentation.md` can update cross-cutting docs that scout typically does not surface as import-edge findings). The set is closed - safety paths are exactly these entries and do not implicitly extend to other gitignored content. `.env*` and `.git/` are never safety paths regardless of scope-artifact contents.
- **Project context** (architecture entry point): `<project-root>/docs/project-context.md` is the canonical entry point to the codebase architecture - written by `apex-init` at project setup and curated by the team thereafter. Read contract is hybrid (NOT blanket - token cost / no decision benefit on most agents). Closed list of readers: main orchestrator at SKILL.md Step 1 (best-effort, absent = silent skip; pre-biases hypothesis + propagates by inheritance to trivial / zero-layer); `planner.md` at p2.0b (architectural boundaries inform disjoint-scope and `shared_files`); `agents/executor.md` (only when slice spans modules or introduces a new abstraction); `agents/documentation.md` at p1.3 / p2.4 (always, doc-layer entry point). Read-skip set: screener (6.c), learn, git, reflector, rescout, all scripts. `docs/**` is already in the safety-paths closed set above so `project-context.md` is always readable from any apex scope. See `skills/apex/shared-guardrails.md` "Project context" for the closed contract.
- **Project lessons paths**: `.claude/lessons-index.md` (curated index; consumed by step 4 `grep-lessons.sh`), `.claude/lessons.md` (curated lessons body), `.claude/lessons-archive.md` (older / superseded entries). `learn.md` (p1.3 / p2.4) appends novel patterns to `.claude-tmp/lessons-tmp.md` for later curation into these files; curation itself is out of scope for /apex.
- **Session token format**: 8-char lowercase hex (short guid, generated by step 2 manifest script via `openssl rand -hex 4` or equivalent). Tight enough that cleanup glob `*{session}*` cannot substring-match unrelated files in `.claude-tmp/`.
- **Session manifest schema** (`.claude-tmp/apex-active/{session}.json`): `{session, pid, cc_session_id, p2_cc_session_id?}` where `cc_session_id` is the Claude Code session id captured at step 2 (entry-flow session) and is never overwritten; `p2_cc_session_id` is appended by p2.0 after the p2.0c context clear (the new Claude Code session id that runs Path 2). `pid` is the OS process id of the Claude Code main process and is never overwritten - Claude Code's plan-mode-exit / context-clear keeps the same OS process, so the original pid stays alive and valid for sibling /apex's step-2 concurrency check throughout the session lifetime. Reflectors locate the TaskList file at `~/.claude/todos/{id}-agent-{id}.json` using the appropriate id: step-10 and p1.4 reflectors read `cc_session_id` (entry-flow / Path 1 stay in the original Claude Code session); p2.5 reflector reads `p2_cc_session_id`. The TaskList file at `~/.claude/todos/{cc_session_id}-agent-{cc_session_id}.json` persists across plan-mode context clear (Claude Code does not delete it on p2.0c), so a step-10 reflector that finishes after p2.0c can still read the entry-flow TaskList.
- **Scope write producers** (single source of truth for `{session}-main-scope.json`, exactly one fires per session): trivial path -> `trivial.md` inline orchestrator `Write` tool; zero-layer proceed -> `scout1.md` 6.a inline orchestrator `Write` tool; normal path -> `verify-claims.sh` (default mode if no claim-review needed, or `--apply-resolved` mode after inline review). Teammate scopes (`{session}-{teammate-id}-scope.json`) are written only by `teammates.md` at p2.1.
- **`verify-claims.sh` modes**: default mode (no flag) runs the full claim verification pass and dispatches via exit code per step 8 gates - **0** writes `{session}-main-scope.json` as its last action and proceeds; **1** aborts (preflight bad OR screened-bad re-run cap reached); **2** signals re-run 6c+7 (screened bad, capped at one rerun); **3** leaves scope unwritten for inline-review (>=3 unresolved) so the orchestrator can re-invoke with `--apply-resolved`. `--apply-resolved` mode skips re-validation (claims already validated), re-reads `screened-{session}.json` + `claim-review-resolved-{session}.json`, re-adds `keep` claims, and unconditionally writes scope as its last action (exits 0). **Exit-code priority** when multiple gates would fire simultaneously: 1 > 2 > 3 > 0 (most-severe wins; preflight failure trumps screening failure trumps unresolved-batch routing). Exit 1 carries an `abort_cause` field in the script's stderr message - `preflight_bad` or `screened_unconverged` - so the orchestrator picks the right user-facing wording (see step 8).
- **Trace path schema**: `.claude-tmp/apex-active/{session}-traces/{phase}/{agent}[-{disambiguator}].md` where `{disambiguator}` is optional and, when present, is one or more dash-joined segments identifying the invocation (shard-id, task-id, teammate-id, teammate-id-task-id, attempt-N). Single-invocation agents omit the disambiguator. Screener and rescout are the special cases: both can run twice when an exit-2 6c+7 re-run fires, so their traces always carry an `attempt-N` disambiguator - `screener-{shard-id}-attempt-1.md` / `rescout-attempt-1.md` for the initial 6.c / 7.x; `screener-{shard-id}-attempt-2.md` / `rescout-attempt-2.md` for the second pass after re-screening (preserves both attempts so the reflector can compare what changed).
- **scope-check hook**: PreToolUse on `Edit` / `Write` / `MultiEdit` / `NotebookEdit` (all file-modification tools that flow through Claude Code's tool-call layer). Bash file operations (`sed -i`, `awk -i`, redirection, `tee`, `cp`, `mv`, etc.) are NOT gated by the hook because Bash runs as a single tool with arbitrary internal commands; subagent and skill prompts must restrict file modifications to the hook-gated tools (convention-enforced at the prompt layer). The hook is the outer guard for tool-driven writes only - bash-driven mutations bypass it by design. Resolves the active scope file via on-disk pointer (env-var indirection rejected: Claude Code's Bash tool runs each invocation in a fresh subshell, so an `export FOO=...` from the agent does not persist to subsequent calls or to the hook subprocess; on-disk state is the only reliable cross-call channel). The hook extracts `session_id` from its stdin event JSON and reads `.claude-tmp/apex-active/{session}-scopes/{session_id}.txt` (single-line file containing the absolute path to the active scope JSON) by globbing `.claude-tmp/apex-active/*-scopes/{session_id}.txt` (any apex `{session}` matches; in practice exactly one matches the calling session_id). The main orchestrator writes its pointer at `{session}-scopes/{cc_session_id}.txt` immediately after each scope write (step 5 trivial path inline `Write`, 6.a zero-layer enumerate, or step 8 `verify-claims.sh`); at p2.0 the main orchestrator additionally writes `{session}-scopes/{p2_cc_session_id}.txt` so the post-context-clear session has a pointer (both point at `{session}-main-scope.json`). Each teammate, at its own p1.0 startup (under `--teammate`), writes `{session}-scopes/{teammate_cc_session_id}.txt` pointing at `{session}-{teammate-id}-scope.json`. Agent-tool subagents (executor, screener, rescout) share the parent's `session_id`, so PreToolUse fires with the parent's `session_id` and the hook resolves through the parent's pointer (the orchestrator's pointer in main / p2 sessions, the teammate's pointer in teammate sessions); no separate per-subagent pointer is needed. TeamCreate teammates are distinct Claude Code sessions with their own `session_id` and write their own pointer at p1.0 (above). While no pointer file matches the calling session_id (entry-flow phase before any pointer is written, or non-/apex Claude Code session), the hook is pass-through. Covers (non-exhaustive) all `Edit` / `Write` from: main-session inline edits, executor subagent writes (p1.1 in main and teammate chains, fix-attempts at p1.2 / p2.3), polish at p1.1b (main and teammate). Teammate scopes MUST be subsets of `{session}-main-scope.json` AND pairwise disjoint (excluding standard safety paths) - see p2.0b "Disjoint-scope rule". If the planner needs a file outside main scope for a teammate, the planner extends `main-scope.json` first (main scope is the union, single source of truth); files that need cross-teammate touch are routed to the planner's `shared_files` list and owned by p2.4's integration pass, not by any teammate scope.

## Entry flow

0. Initialisation
   - /apex (main orchestrator) | `~/.claude/skills/apex`
     - TaskCreate below tasks 1. to 5.
1. Analyze
   - inline task prompt
     - analyzes prompt
     - AskUserQuestion if ambiguous (assuming = forbidden)
     - reads `<project-root>/docs/project-context.md` if present (best-effort; absent = silent skip). The architecture entry point pre-biases Step 3 hypothesis (architecture terms surface in `hypothesis` and `alternatives`) and propagates by inheritance through working memory to the trivial / zero-layer branches. Hybrid depth - downstream consumers (planner / executor / documentation) re-read directly when their work requires it; scout / screener / learn / git / reflector skip. See Conventions / Project context.
2. Create session manifest (concurrent session mitigation) | Blocked by #1
   - script reads `.claude-tmp/apex-active/*.json`, detects active sessions (manifest exists AND PID alive AND `/proc/<pid>/comm` or `ps -o comm= -p <pid>` matches `claude` - guards against PID rollover after reboot or long uptime where a recycled PID could match an unrelated process). The pid stored in each manifest is the Claude Code main-process pid, captured via `$PPID`: inside Claude Code's Bash tool the spawned shell's parent IS the Claude Code main process - verifiable by `ps -o pid,ppid,command -p $PPID` showing the `claude --session-id ...` invocation, and `$PPID` uniquely identifies this conversation's claude process even when multiple concurrent claude sessions exist on the machine (where `pgrep claude` would return all of them ambiguously). NOT the script's own pid - that dies on script exit and would always look stale. Manifests with dead or mismatched PIDs are treated as stale.
   - on overlap: AskUserQuestion with options filtered to detected state - `abort` is always presented; `proceed alongside` is presented only when at least one ACTIVE session is detected; `cleanup-stale-and-proceed` is presented only when at least one STALE manifest is detected (at least one non-abort option is always present, since "overlap" requires at least one of active or stale; if the user dismisses or cancels the question without picking an option, treat as abort)
     - "proceed alongside": new `{session}` token issued; both sessions run in parallel (all artifacts are session-keyed so no collision)
     - "cleanup-stale": for each stale manifest, invoke `session-end-hook.sh <stale-session-token>` (script accepts an optional positional arg; when supplied, the script targets that apex session token directly; when invoked by Claude Code's SessionEnd hook with no arg, it reads `session_id` from the hook's stdin JSON and matches against active manifests' `cc_session_id` / `p2_cc_session_id` to derive the apex session token); then proceed with a new token
   - on no overlap (or after resolution): script creates `{session}` token + session manifest in `.claude-tmp/apex-active/`
3. Hypothesis (be careful, prompt may bias/narrow actual scope implied by user) | Blocked by #2
   - inline task prompt
     - emits hypothesis
     - emits `complexity_hint: low|medium|high`
     - emits `alternatives: [...]` - 1-3 narrower/broader scope interpretations, each marked kept/rejected with one-line reason (structured anti-bias check, not vibes)
     - writes `.claude-tmp/apex-active/{session}-hypothesis.json` with schema `{original_prompt: string (verbatim), hypothesis: string, complexity_hint: 'low'|'medium'|'high', alternatives: [{interpretation: string, status: 'kept'|'rejected', reason: string}]}` (single file persisted for shard-script consumption via `jq`, reflector analysis, and end-of-session summary)
4. Load lessons | Blocked by #3
   - inline task prompt
     - runs `grep-lessons.sh` from hypothesis keywords from previous step
     - runs `update-hit.sh` (lesson hit-tracking) with matched lesson IDs from grep-lessons.sh
5. Trivial task detection -> if trivial, jump to Path 1 | Blocked by #4
   - inline task prompt
     - scout-skip detection: single file, no cross-file deps in hypothesis, no new abstractions
     - trivial detection trades fidelity for latency; if the inline task is uncertain, default to non-trivial
     - returns trivial|non-trivial
   - if trivial: orchestrator writes `.claude-tmp/apex-active/{session}-main-scope.json` inline via the `Write` tool (allowed-files = detected single file + standard safety paths; see Conventions / Scope write producers), then writes the scope-check pointer at `.claude-tmp/apex-active/{session}-scopes/{cc_session_id}.txt` (single line: absolute path to the scope file just written; see Conventions / scope-check hook), then calls p1.md | `~/.claude/skills/apex/p1.md`
   - if non-trivial: TaskCreate below tasks 6. to 9.
6. Scout phase 1 (enumerate -> shard -> screen) against hypothesis
   - Artifacts written to `.claude-tmp/scout/`
   - scout1.md | `~/.claude/skills/apex/scout1.md`
     - TaskCreate (insert before task 7.) the 3 below tasks
       - 6.a enumerate (deterministic enumeration)
         - runs scripts (generates `findings-{session}.json`)
           - Deterministic layers (priority order, each layer optional):
             1. Static imports (project-native parser: madge / pydeps / etc. - explicit dependencies, zero noise)
             2. ast-grep structural queries (tree-sitter, language-aware - call sites, type usages, dynamic imports folded in)
             3. LSP references (when an LSP server is up and responsive)
             4. Framework-convention scans (Next.js routes, Rails conventions, etc.)
           - Fallback only: ripgrep text patterns, runs only when 0 of the 4 deterministic layers produced any finding (a layer is treated as having "succeeded" only if it executed AND emitted >= 1 finding; layers that ran cleanly but returned empty are treated the same as layers that did not run, so ripgrep fires whenever the deterministic merge is empty). Ripgrep is the noise generator - matches strings in comments / docstrings / JSON; demoted to last resort.
           - All script-driven, ground truth list. Layer outputs merged into `findings-{session}.json`:
             - Dedupe by file path, canonicalized via `realpath` (avoids `./foo` vs `foo` vs absolute-path mismatches)
             - Each entry carries `reasons: [{layer: static-imports|ast-grep|lsp|framework|ripgrep|rescout, detail: '...', line_range: [start, end] | null}]` - one item per layer that matched the file; `line_range` populated when the layer reports it (ast-grep, lsp, framework, rescout match locations), null otherwise (static-imports, ripgrep file-level hits). The `rescout` layer is reserved for entries merged in by 7.x targeted rescout (see step 7.x); it never appears in the initial 6.a output.
             - Same-layer duplicate reasons collapsed by `detail` string (a single layer reporting the same file twice with the same reason becomes one entry)
             - `confidence: high|medium|low` derived from layer count (3+ deterministic layers = high; 1-2 = medium; ripgrep-only = low). The `rescout` layer is special-cased at 7.x merge time (medium by default; explicit `line_range` promotes to high; see step 7.x) and does not participate in this layer-count formula. Consumed downstream: screener (6.c) biases keep/drop on `low` (drop unless positive relevance signal) and `high` (keep unless clear negative); verify (8) downgrades `low` claims with no `line_range` to unresolved-claim review rather than auto-confirmed.
           - Graceful degradation: if some layers unavailable, surviving deterministic layers run. If 0 deterministic layers run, ripgrep fallback fires with `_meta.warnings: ['no deterministic layers ran - ripgrep-only fallback']` appended to `findings-{session}.json`.
           - Zero-layer case: if all 4 deterministic layers AND ripgrep fallback produce 0 findings, enumerate writes empty `findings-{session}.json` with `_meta.warnings: ['no layers produced findings']` and exits with a sentinel exit code (e.g., 10) signalling zero-layer to the orchestrator. The orchestrator surfaces via AskUserQuestion ("no scope detected - hypothesis may need refinement; abort or proceed with prompt-mentioned files only?"). On proceed: orchestrator runs `bash skills/apex/scripts/zero-layer-extract.sh {session}` (single positional arg, reads `$CC_SESSION_ID` from env). The script parses `original_prompt` from `{session}-hypothesis.json` for explicit file path tokens (regex-extracted: paths matching the project root tree, plus quoted/backtick-wrapped relative paths), validates each path exists on disk, writes `.claude-tmp/apex-active/{session}-main-scope.json` (allowed-files = extracted-and-validated paths + standard safety paths), and writes the scope-check pointer at `.claude-tmp/apex-active/{session}-scopes/{cc_session_id}.txt` (single line: absolute path to the scope file). Script exits 10 on zero validated paths (orchestrator runs the verify-exit-1 abort surface). The pipeline then SKIPS steps 6.b, 6.c, 7, 8, AND 9 (no shards, no screening, no claim verification, no path decision - there are no findings to process and the path is forced to trivial-equivalent Path 1) and the orchestrator calls p1.md directly with NO preflight artifact written (matches the trivial-detection branch at step 5; p1.0 reads an absent preflight and runs the no-findings-consultation branch uniformly across both trivial and zero-layer cases). The orchestrator marks the queued tasks 6.b, 6.c, 7, 8, and 9 as completed (skipped, no-op) before invoking p1.md so the TaskList reflects reality. If `original_prompt` yields zero validated file paths, the orchestrator aborts with the same surface as a verify exit-1 (and runs `session-end-hook.sh {session}` inline per "Mid-/apex abort cleanup"). On abort (user choice or cancelled question): orchestrator runs `session-end-hook.sh {session}` inline and exits cleanly.
         - returns `findings-{session}.json` to apex
       - 6.b shard (preflight sizing + shard plan) | Blocked by #6.a
         - shard script
           - reads `findings-{session}.json`
           - decides mechanically: shard count = `ceil(files / 15)` (15 files per screener keeps Sonnet context comfortable), shard boundaries (by top-level dir, file-type, or import-edge cluster)
           - if shard count > 8: emit warning to `_meta.warnings` and surface to user via AskUserQuestion ("scope likely overshot - N shards needed; continue or refine prompt?"). On user-continue, no max cap; on refine, abort cleanly. If the user dismisses or cancels the question without picking an option, treat as abort.
           - reads hypothesis from `.claude-tmp/apex-active/{session}-hypothesis.json` (path passed as CLI arg)
           - emits shared screening prompt template with hypothesis injected verbatim
           - generates `shard-plan-{session}.json` with `{shards: [...], screening_prompt: "..."}`
           - returns `shard-plan-{session}.json` path to apex
       - 6.c screen (parallel LLM screening) | Blocked by #6.b
         - spawns parallel screener subagents per `shard-plan-{session}.json`
         - screener.md | `~/.claude/agents/screener.md` (Sonnet latest subagent, high effort by default)
           - follows given screening task: gets its shard + hypothesis, returns keep/drop + relevance annotation per file
           - writes structured shard-result to `.claude-tmp/scout/shard-{shard-id}-{session}.json`: `{kept: [{file, screener_reason, reasons, confidence}], dropped: [{file, screener_reason}]}` where `screener_reason` is the screener's free-text keep/drop justification, and `reasons` + `confidence` are forwarded verbatim from the screener's input findings entry (the layer-attribution array - same shape as findings.json - and confidence are computed at 6.a and must propagate through screen + aggregate so verify (8) can apply confidence-aware screening on `screened-{session}.json`); schema-validated
           - writes prose claim-provenance trace to `.claude-tmp/apex-active/{session}-traces/entryflow/screener-{shard-id}-attempt-N.md` (kept/dropped narrative + one-line reason per drop). N is `1` for the initial 6.c run; if step 8 returns exit-2 and 6.c re-runs, that second pass writes `screener-{shard-id}-attempt-2.md` so the first attempt's reasoning is preserved alongside the second.
           - returns the shard-result JSON path + one-line status to apex, never the findings body
         - scout1.md (the step 6 owner) aggregates: reads each shard-result JSON, merges per-shard kept / dropped lists into `screened-{session}.json`, validates against schema, returns the merged artifact path to apex
7. Scout phase 2 preflight -> select medium or complex mode (rescout if gaps) | Blocked by #6
   - scout2.md | `~/.claude/skills/apex/scout2.md`
     - reads `screened-{session}.json` + prompt
     - computes `effective_blast`: `small` if kept-file count <= 15 AND shard count == 1; `large` otherwise. Both terms are needed: shard count comes from pre-screen findings count (6.b), kept-file count is post-screen - `small` requires the work to have been narrow both before and after screening (a wide pre-screen scope that screening culled to <= 15 still indicates non-trivial blast and routes to `large` / Path 2)
     - Writes `preflight-{session}.json` to `.claude-tmp/scout/`: `{missed_regions: [{file, line_range: [start, end] | null, reason}], effective_blast: small|large, mode: medium|complex}`
     - Gate:
       - `missed_regions=[]` AND `effective_blast=small` -> medium mode, proceed to 8
       - `missed_regions=[]` AND `effective_blast=large` -> complex mode, proceed to 8 (no rescout - nothing to look for)
       - `missed_regions != []` -> complex mode, TaskCreate 7.x
   - 7.x Targeted rescout (only if gate triggered, insert before task 8.)
     - rescout.md | `~/.claude/agents/rescout.md` (Sonnet latest subagent)
       - re-enumerates `missed_regions`
       - writes `rescout-{session}.json` to `.claude-tmp/scout/`
       - writes trace to `.claude-tmp/apex-active/{session}-traces/entryflow/rescout-attempt-N.md` where N is `1` for the initial 7.x; if step 8 returns exit-2 and the 6c+7 re-run produces newly-missed regions that trigger a second rescout, that second pass writes `rescout-attempt-2.md` (regions queried, files newly found, why prior pass missed them)
       - run `merge-scout-findings.py` to merge into `screened-{session}.json`. Rescout findings are merged as kept (pre-trusted, no re-screening) - rationale: preflight already named the missed region as relevant, so the keep/drop signal has been delivered upstream; running another screener pass on already-vetted regions wastes a Sonnet call. Rescout-merged entries carry `reasons: [{layer: rescout, ...}]` so downstream verify (8) can still apply confidence-aware screening (rescout entries are treated as `confidence: medium` by default; explicit line_range from rescout promotes to `high`). Dedupe rules at merge time (file paths canonicalized via `realpath`): if file is already in `kept`, append `{layer: rescout, ...}` to its existing `reasons` array (confidence stays as the deterministic-layer-count-derived value, since rescout is special-cased out of the formula); if file is already in `dropped`, move it from `dropped` to `kept` with `reasons: [{layer: rescout, ...}]` and the rescout-derived confidence (rescout overrides screener-drop because preflight explicitly named the region relevant); if file is not present in either list, add as new `kept` entry.
       - task 7.x does not re-trigger preflight (complex mode is sticky)
8. Verify claims (anti-hallucination) | Blocked by #7
   - `verify-claims.sh` (script) verifies claims
     - Reads `screened-{session}.json` and `preflight-{session}.json` from `.claude-tmp/scout/`
     - For each claim (file path + reason, plus `line_range` when present): verify file exists; if `line_range` is present, re-read the cited range and confirm content is non-empty and in-bounds; if `line_range` is null, file-existence check is sufficient
     - Drop mechanically-failed claims from both files (file missing, or `line_range` present but out-of-bounds / empty). For `screened-{session}.json` writes `_meta.dropped_per_layer: {static-imports: N, ast-grep: N, lsp: N, framework: N, ripgrep: N, rescout: N}` back into the file (claims carry layer attribution); for `preflight-{session}.json` writes `_meta.dropped_count: N` (missed_regions claims have no layer attribution). Schema stays self-describing per artifact.
     - Confidence-aware screening: for any claim in `screened-{session}.json` with `confidence: low` AND no `line_range`, route to unresolved-claim review instead of auto-confirming (delivers on the promise in 6.a). Routed claims are removed from `screened-{session}.json` at routing time (not auto-confirmed) and re-added only if the review keeps them.
     - Emit unresolved claims (mechanically valid, but reason-string semantic match unclear, OR low-confidence with no line_range) to `.claude-tmp/scout/claim-review-{session}.json` for optional main-orchestrator review. Both types of unresolved are removed from `screened-{session}.json` at emission time (the removal rule above for low-confidence-no-range applies uniformly to all unresolveds, not just that subset) and re-added only if the orchestrator's inline review keeps them on exit-3
     - Gates (absolute counts primary; percent threshold as safety net on larger claim sets) - distinct exit codes so the orchestrator can dispatch. **Priority when multiple would fire**: 1 > 2 > 3 > 0 (most-severe wins; preflight failure trumps screening failure trumps unresolved-batch routing):
       - `preflight_bad >= 2` -> **exit 1** with `abort_cause=preflight_bad` written to stderr (abort and surface to user; preflight drives path selection; cannot proceed on shaky ground). Orchestrator surfaces hypothesis text from `{session}-hypothesis.json` with message "Hypothesis may be wrong - review and re-prompt"
       - `screened_bad >= 3` OR `screened_bad_rate >= 30%` (either condition triggers; `screened_bad_rate = screened_bad / total_screened_claims` where `total_screened_claims` is the count of claims read from `screened-{session}.json` at this verify pass) -> **exit 2** (re-run 6c AND step 7 preflight - re-screening can materially change kept-files, which invalidates `effective_blast` / `mode` / `missed_regions`; preflight is cheap and must reflect the latest screened set so step 9 dispatches correctly. Re-running 7 may again trigger 7.x rescout if newly missed regions appear; the same exit-2 cap below covers the entire 6c+7 re-run as one attempt. Cap at one re-run per session tracked in `.claude-tmp/apex-active/{session}-verify-rerun.json` schema `{count: int, last_attempt_at: ISO-8601 string}` (dedicated file, not in `_meta`, to survive aggregator rewrites of `screened-{session}.json`); first exit-2 finds no file, writes `{count: 1, last_attempt_at: ...}`, and re-runs; second exit-2 reads `count >= 1` and emits **exit 1** with `abort_cause=screened_unconverged` written to stderr - orchestrator then surfaces "Scout could not converge after re-screening - review hypothesis and re-prompt" instead of the preflight-bad message)
       - `len(unresolved_claims) >= 3` -> **exit 3** (scope unwritten; orchestrator does inline review then re-invokes `verify-claims.sh --apply-resolved`)
       - Otherwise -> **exit 0**, scope written, proceed with cleaned files
     - Orchestrator dispatches on `$?`: 0 = proceed, 1 = abort (read `abort_cause` from stderr to pick user message), 2 = re-run 6c+7, 3 = inline review
   - Main orchestrator branches on exit code: exit 0 means scope is written and `claim-review-{session}.json` (if any unresolved exists) has < 3 entries - those small-batch unresolveds stay dropped (matches the "instead of auto-confirming" rule above - small-batch skip favours safety). ## Artifact validation (JSON Schema)

Cross-step JSON artifacts are validated against schemas at `~/.claude/skills/apex/schemas/*.schema.json`. Schemas are the source-of-truth contract between pipeline steps.

- Validated artifacts: `findings-{session}.json`, `shard-{shard-id}-{session}.json`, `shard-plan-{session}.json`, `screened-{session}.json`, `preflight-{session}.json`, `rescout-{session}.json`, `claim-review-{session}.json`, `claim-review-resolved-{session}.json`, `{session}.json` (session manifest), `{session}-hypothesis.json`, `{session}-fix-attempts-{context}.json` (one per fix-attempt context: `main` for Path 1 p1.2, `p2` for central Path 2 p2.3 - teammate-mode p1.2 is skipped so no per-teammate context exists), `{session}-verify-rerun.json`, `{session}-baseline.json`, `{session}-main-scope.json`, `{session}-{teammate-id}-scope.json`

- Lean: ~50 lines of shared validation helper used everywhere; reduces "downstream skill chokes on malformed JSON" failure mode at zero token cost

## Trace files (opt-in)

For agents whose internal reasoning matters (provenance, failure analysis), the agent writes a trace before returning its summary. Path schema is defined in Conventions.

## Failure handling

- `cleanup-session.sh` is idempotent: exit 0 on partial cleanup with warnings written to stderr. Orchestrator never blocked on cleanup. Entry points: success-path steps (p1.5 / p2.6) call `cleanup-session.sh` directly; SessionEnd / mid-abort cleanup goes through `session-end-hook.sh` (which wraps `cleanup-session.sh` plus a hypothesis-file fallback) - the inner `cleanup-session.sh` is shared and idempotent across both entry points. Does NOT touch `{session}-hypothesis.json` - it is consumed downstream by p1.6 / p2.7 inline summary, which cleans it up on success.
- `session-end-hook.sh` (SessionEnd) wraps `cleanup-session.sh` and additionally removes `{session}-hypothesis.json` if still present (belt-and-suspenders fallback when consumer fails). When invoked by Claude Code's SessionEnd hook (no positional arg), it reads `session_id` from the hook's stdin JSON and matches against active manifests' `cc_session_id` / `p2_cc_session_id` to derive the apex session token. When invoked manually with a positional arg (cleanup-stale at step 2, or any orchestrator-driven cleanup), it uses that token directly. Runs on success completion AND on abort / crash. Idempotent. Replaces the prior plain `cleanup-session.sh` SessionEnd invocation so stale manifests do not poison concurrency detection.
- **Mid-/apex abort cleanup**: any orchestrator exit that bypasses p1.5 / p2.6 (verify exit-1 abort - either `preflight_bad` or `screened_unconverged`; AskUserQuestion-abort at step 2 / step 6.a zero-layer / 6.b / p1.0 / p2.0; zero-layer "no validated paths" abort from step 6.a; teammate-failure abort) should run `session-end-hook.sh {session}` inline before returning, mirroring the explicit p2.0c plan-mode-rejection branch. The Claude Code SessionEnd hook is the catch-all when the entire Claude Code session ends; the inline call handles the "user aborts /apex but stays in the same Claude Code session" case so the manifest does not orphan and trigger false-positive concurrency detection from sibling /apex calls.

- **p2.4** Tail (learn / documentation / git) | Blocked by #p2.3
  - script `detect-tail-mode.sh` reads `head_sha` from `{session}-baseline.json` and computes the size signal across both tracked-modified and untracked files: `FILE_COUNT = (git diff --name-only {baseline.head_sha}; git ls-files --others --exclude-standard) | sort -u | wc -l`; `LINE_DELTA = additions+deletions from git diff --shortstat {baseline.head_sha} PLUS sum of wc -l across untracked files` (untracked must be counted explicitly because `git diff` excludes them - a new file teammates created would otherwise contribute zero lines).     - documentation.md | `~/.claude/agents/documentation.md` (project-specific; reads `git diff {baseline.head_sha}` for context (head_sha sourced from `.claude-tmp/apex-active/{session}-baseline.json`; baseline-pinned for the same race-avoidance reason as learn.md); integration pass in Path 2 - owns first-write on the planner's `shared_files` list (excluded from every teammate scope by the disjoint-scope rule at p2.0b - typically shared READMEs / top-level architecture docs that multiple teammates' work touches conceptually) AND updates project-level architecture notes when structural changes warrant. Per-teammate scope-internal doc edits happened in each teammate's p1.3; this pass owns whatever crosses teammate boundaries)
    - git.md | `~/.claude/agents/git.md` (reads `head_sha` from `.claude-tmp/apex-active/{session}-baseline.json`, stages `(git diff --name-only {baseline.head_sha}; git ls-files --others --exclude-standard) | sort -u` - covers teammate-modified tracked files AND teammate-newly-created untracked files; the latter is REQUIRED because `git diff` excludes untracked, so a new file teammates created would otherwise never get committed. Staging is per-file `git add` rather than `git add -A`, after a denylist pre-filter that skips any path whose basename is in the dotenv-secret set `{.env, .env.local, .env.production, .env.development}` or any path matched by `git check-ignore` (covers `.claude-tmp/` and the project's `.gitignore`). The explicit dotenv-secret basename denylist guards against secret leakage even when a project's `.gitignore` is incomplete. The denylist is a closed set (not a `.env*` glob) so legitimately committable templates like `.env.example` still get staged. Pre-/apex dirty files surviving the p2.0 conflict check are staged alongside apex's edits per the "process as normal file" rule).

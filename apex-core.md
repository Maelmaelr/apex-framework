# /apex v1.0

Apex is the main orchestrator in the main session.

For a lighter, easier-to-read summary of steps, skill/agent/script used, and routing conditions, see `apex-core-overview.md`.

## Effort levels (cross-cutting)

- Step 3 (hypothesis): emits `complexity_hint: low|medium|high` - heuristic estimate from prompt signals (verb scope, file / module names mentioned, abstraction-level keywords). Refined nowhere; consumed as-is by p2.0b.
- Step 6.c (screeners): high effort by default (classification quality matters; cost amortised across parallel shards).
- p2.0b (planner): per-teammate effort decided from `complexity_hint` + scope size; high-effort keyword fires when `complexity_hint == high`.

## Conventions

- **Standard safety paths** (always allowed in any scope artifact): `.claude-tmp/`, `~/.claude/tmp/`, `~/.claude/plans/` (plan-mode artifacts; orchestrator-owned, not part of any apex scope), `/tmp/{session}-*`, project `docs/**`, and any `README*` file at any depth (so `documentation.md` can update cross-cutting docs that scout typically does not surface as import-edge findings). The set is closed - safety paths are exactly these entries and do not implicitly extend to other gitignored content. `.env*` and `.git/` are never safety paths regardless of scope-artifact contents.
- **Project context** (architecture entry point): `<project-root>/docs/project-context.md`; see `skills/apex/shared-guardrails.md` "Project context" for the closed hybrid read contract (which readers / which skip; `docs/**` already in safety-paths so always readable).
- **Project lessons paths**: `.claude/lessons-index.md` (curated index; consumed by step 4 `grep-lessons.sh`), `.claude/lessons.md` (curated lessons body), `.claude/lessons-archive.md` (older / superseded entries). `learn.md` (p1.3 / p2.4) appends novel patterns to `.claude-tmp/lessons-tmp.md` for later curation into these files; curation itself is out of scope for /apex.
- **Session token format**: 8-char lowercase hex (short guid, generated by step 2 manifest script via `openssl rand -hex 4` or equivalent). Tight enough that cleanup glob `*{session}*` cannot substring-match unrelated files in `.claude-tmp/`.
- **cc_session_id resolution**: Claude Code does NOT export the active session id as a bash env var. Every apex script that needs `cc_session_id` resolves through the canonical `scripts/get-cc-session-id.sh` helper (env-var fast path then most-recent-jsonl fallback at `~/.claude/projects/<encoded-cwd>/`, where `<encoded-cwd> = pwd | tr '/.' '--'`). Step 2 invokes `create-session.sh --cc-session-id "$(bash scripts/get-cc-session-id.sh)"`; 6.a `zero-layer-extract.sh` falls back to the helper when `CC_SESSION_ID` env is unset; any future script that names `cc_session_id` MUST source the helper rather than re-implement the lookup. See `skills/apex/shared-guardrails.md` "cc_session_id resolution" for the same recipe used by all callers.
- **JSON Schema validation helpers**: `scripts/_validate.py` (python module - `producer_validate(data, schema_name)` raises `ValidationError`; `consumer_load(path, schema_name)` returns `None` on missing/invalid; schema dir resolved via `APEX_SCHEMA_DIR` env var if set + non-empty, otherwise defaults to `skills/apex/schemas/` relative to the module) and `scripts/validate-json.sh [--admin] <schema-name> <json-path>` (thin shell wrapper around `producer_validate`; `--admin` exports `APEX_SCHEMA_DIR=skills/admin-apex/schemas/` before invoking python - no runtime monkey-patch). Used by `create-session.sh` after manifest write and by orchestrator inline-LLM producers (Step 3 hypothesis) immediately after `Write`. Single uniform call site for the producer-validates-before-write rule across script + inline-LLM producers. Apex hot path falls back to JSON-parse-only when `jsonschema` is not importable (one-line stderr warning per process; end-user environments without the dep stay unblocked); admin-apex enforces strict mode via `scripts/check-deps.sh` at task 1 (hard fail with install one-liner if `jsonschema` missing - the maintenance path owns mutation and must validate before write).
- **Session manifest schema** (`.claude-tmp/apex-active/{session}.json`): `{session, pid, cc_session_id, p2_cc_session_id?}` where `cc_session_id` is the Claude Code session id captured at step 2 (entry-flow session) and is never overwritten; `p2_cc_session_id` is appended by p2.0 after the p2.0c context clear (the new Claude Code session id that runs Path 2). `pid` is the OS process id of the Claude Code main process and is never overwritten - Claude Code's plan-mode-exit / context-clear keeps the same OS process, so the original pid stays alive and valid for sibling /apex's step-2 concurrency check throughout the session lifetime. Reflectors locate the TaskList file at `~/.claude/todos/{id}-agent-{id}.json` using the appropriate id: step-10 and p1.4 reflectors read `cc_session_id` (entry-flow / Path 1 stay in the original Claude Code session); p2.5 reflector reads `p2_cc_session_id`. The TaskList file at `~/.claude/todos/{cc_session_id}-agent-{cc_session_id}.json` persists across plan-mode context clear (Claude Code does not delete it on p2.0c), so a step-10 reflector that finishes after p2.0c can still read the entry-flow TaskList.
- **Scope write producers** (single source of truth for `{session}-main-scope.json`, exactly one fires per session): trivial path -> `trivial.md` inline orchestrator `Write` tool; zero-layer proceed (and 6.b cap-overshoot proceed-with-prompt-paths, which reuses the same writer) -> `scripts/zero-layer-extract.sh` (the script writes scope + pointer; orchestrator MUST NOT pre-write or post-write freehand); normal path -> `verify-claims.sh` (default mode if no claim-review needed, or `--apply-resolved` mode after inline review). Teammate scopes (`{session}-{teammate-id}-scope.json`) are written only by `teammates.md` at p2.1.
- **`verify-claims.sh` modes**: default mode (no flag) runs the full claim verification pass and dispatches via exit code per step 8 gates - **0** writes `{session}-main-scope.json` as its last action and proceeds; **1** aborts (preflight bad OR screened-bad re-run cap reached); **2** signals re-run 6c+7 (screened bad, capped at one rerun); **3** leaves scope unwritten for inline-review (>=3 unresolved) so the orchestrator can re-invoke with `--apply-resolved`. `--apply-resolved` mode skips re-validation (claims already validated), re-reads `screened-{session}.json` + `claim-review-resolved-{session}.json`, re-adds `keep` claims, and unconditionally writes scope as its last action (exits 0). **Exit-code priority** when multiple gates would fire simultaneously: 1 > 2 > 3 > 0 (most-severe wins; preflight failure trumps screening failure trumps unresolved-batch routing). Exit 1 carries an `abort_cause` field in the script's stderr message - `preflight_bad` or `screened_unconverged` - so the orchestrator picks the right user-facing wording (see step 8).
- **Trace path schema**: `.claude-tmp/apex-active/{session}-traces/{phase}/{agent}[-{disambiguator}].md` where `{disambiguator}` is optional and, when present, is one or more dash-joined segments identifying the invocation (shard-id, task-id, teammate-id, teammate-id-task-id, attempt-N). Single-invocation agents omit the disambiguator. Screener and rescout are the special cases: both can run twice when an exit-2 6c+7 re-run fires, so their traces always carry an `attempt-N` disambiguator - `screener-{shard-id}-attempt-1.md` / `rescout-attempt-1.md` for the initial 6.c / 7.x; `screener-{shard-id}-attempt-2.md` / `rescout-attempt-2.md` for the second pass after re-screening (preserves both attempts so the reflector can compare what changed).
- **scope-check hook**: PreToolUse on `Edit` / `Write` / `MultiEdit` / `NotebookEdit` (all file-modification tools that flow through Claude Code's tool-call layer). Bash file operations (`sed -i`, `awk -i`, redirection, `tee`, `cp`, `mv`, etc.) are NOT gated by the hook because Bash runs as a single tool with arbitrary internal commands; subagent and skill prompts must restrict file modifications to the hook-gated tools (convention-enforced at the prompt layer). The hook is the outer guard for tool-driven writes only - bash-driven mutations bypass it by design. Resolves the active scope file via on-disk pointer (env-var indirection rejected: Claude Code's Bash tool runs each invocation in a fresh subshell, so an `export FOO=...` from the agent does not persist to subsequent calls or to the hook subprocess; on-disk state is the only reliable cross-call channel). The hook extracts `session_id` from its stdin event JSON and reads `.claude-tmp/apex-active/{session}-scopes/{session_id}.txt` (single-line file containing the absolute path to the active scope JSON) by globbing `.claude-tmp/apex-active/*-scopes/{session_id}.txt` (any apex `{session}` matches; in practice exactly one matches the calling session_id). The main orchestrator writes its pointer at `{session}-scopes/{cc_session_id}.txt` immediately after each scope write (step 5 trivial path inline `Write`, 6.a zero-layer enumerate, or step 8 `verify-claims.sh`); at p2.0 the main orchestrator additionally writes `{session}-scopes/{p2_cc_session_id}.txt` so the post-context-clear session has a pointer (both point at `{session}-main-scope.json`). Each teammate, at its own p1.0 startup (under `--teammate`), writes `{session}-scopes/{teammate_cc_session_id}.txt` pointing at `{session}-{teammate-id}-scope.json`. Agent-tool subagents (executor, screener, rescout) share the parent's `session_id`, so PreToolUse fires with the parent's `session_id` and the hook resolves through the parent's pointer (the orchestrator's pointer in main / p2 sessions, the teammate's pointer in teammate sessions); no separate per-subagent pointer is needed. TeamCreate teammates are distinct Claude Code sessions with their own `session_id` and write their own pointer at p1.0 (above). While no pointer file matches the calling session_id (entry-flow phase before any pointer is written, or non-/apex Claude Code session), the hook is pass-through. Covers (non-exhaustive) all `Edit` / `Write` from: main-session inline edits, executor subagent writes (p1.1 in main and teammate chains, fix-attempts at p1.2 / p2.3), polish at p1.1b (main and teammate). Teammate scopes MUST be subsets of `{session}-main-scope.json` AND pairwise disjoint (excluding standard safety paths) - see p2.0b "Disjoint-scope rule". If the planner needs a file outside main scope for a teammate, the planner extends `main-scope.json` first (main scope is the union, single source of truth); files that need cross-teammate touch are routed to the planner's `shared_files` list and owned by p2.4's integration pass, not by any teammate scope.

     - TaskCreate below tasks 1. to 5.
1. Analyze
   - inline task prompt
     - analyzes prompt
     - AskUserQuestion if ambiguous (assuming = forbidden)
     - reads `<project-root>/docs/project-context.md` if present (best-effort; absent = silent skip). The architecture entry point pre-biases Step 3 hypothesis (architecture terms surface in `hypothesis` and `alternatives`) and propagates by inheritance through working memory to the trivial / zero-layer branches. Hybrid depth - downstream consumers (planner / executor / documentation) re-read directly when their work requires it; scout / screener / learn / git / reflector skip. See Conventions / Project context.
2. Create session manifest (concurrent session mitigation) | Blocked by #1
   - cc_session_id resolution: orchestrator passes `--cc-session-id "$(bash scripts/get-cc-session-id.sh)"` (canonical helper - env-var fast path then latest-jsonl fallback at `~/.claude/projects/<encoded-cwd>/`; see Conventions / cc_session_id resolution). Same helper sourced by 6.a `zero-layer-extract.sh` when env unset.
   - script reads `.claude-tmp/apex-active/*.json` via single python pass (one spawn for the whole scan, not per-manifest), detects active sessions (manifest exists AND PID alive AND `/proc/<pid>/comm` or `ps -o comm= -p <pid>` matches `claude` - guards against PID rollover after reboot or long uptime where a recycled PID could match an unrelated process). The pid stored in each manifest is the Claude Code main-process pid, captured via `$PPID`: inside Claude Code's Bash tool the spawned shell's parent IS the Claude Code main process - verifiable by `ps -o pid,ppid,command -p $PPID` showing the `claude --session-id ...` invocation, and `$PPID` uniquely identifies this conversation's claude process even when multiple concurrent claude sessions exist on the machine (where `pgrep claude` would return all of them ambiguously). NOT the script's own pid - that dies on script exit and would always look stale. Manifests with dead or mismatched PIDs are treated as stale.
   - on overlap: AskUserQuestion with options filtered to detected state - `abort` is always presented; `proceed alongside` is presented only when at least one ACTIVE session is detected; `cleanup-stale-and-proceed` is presented only when at least one STALE manifest is detected (at least one non-abort option is always present, since "overlap" requires at least one of active or stale; if the user dismisses or cancels the question without picking an option, treat as abort)
     - "proceed alongside": new `{session}` token issued; both sessions run in parallel (all artifacts are session-keyed so no collision)
     - "cleanup-stale": for each stale manifest, invoke `session-end-hook.sh <stale-session-token>` (script accepts an optional positional arg; when supplied, the script targets that apex session token directly; when invoked by Claude Code's SessionEnd hook with no arg, it reads `session_id` from the hook's stdin JSON and matches against active manifests' `cc_session_id` / `p2_cc_session_id` to derive the apex session token); then proceed with a new token
   - on no overlap (or after resolution): script creates `{session}` token + session manifest in `.claude-tmp/apex-active/` via `printf` (3-field JSON), then producer-validates against `manifest.schema.json` via `validate-json.sh` (the cc_session_id arg is shape-checked at script entry to harden the printf write against injection)
3. Hypothesis (be careful, prompt may bias/narrow actual scope implied by user) | Blocked by #2
   - inline task prompt
     - emits hypothesis
     - emits `complexity_hint: low|medium|high`
     - emits `alternatives: [...]` - 1-3 narrower/broader scope interpretations, each marked kept/rejected with one-line reason (structured anti-bias check, not vibes)
     - emits `discovered_paths: [<paths>]` (optional) - validated repo-relative file paths captured via bounded inline `Glob` / `Grep` / `Read` exploration when `original_prompt` names no file paths (conceptual prompts like "fix the maintenance banner"). Cap exploration at ~5 calls; persist only paths that exist on disk. Empty / absent when the prompt itself names paths (regex extraction at step 4 keyword derivation + step 6.a `_enumerate.py:extract_seeds` covers them) OR when the prompt is too abstract for the orchestrator to identify candidates without speculation. **Why**: drives autonomous routing at 6.a zero-layer (see step 6.a) and feeds the deterministic enumeration layers as seed_paths so static-imports / framework / lsp can expand from them. Without this, conceptual prompts that the LLM CAN identify files for would still hit zero-layer + AskUserQuestion + abort - wasting the inline-discovery work the orchestrator already did.
     - writes `.claude-tmp/apex-active/{session}-hypothesis.json` with schema `{original_prompt: string (verbatim), hypothesis: string, complexity_hint: 'low'|'medium'|'high', alternatives: [{interpretation: string, status: 'kept'|'rejected', reason: string}] (1-3 entries, schema-required minItems: 1 - structured anti-bias check is non-negotiable), discovered_paths?: [string] (optional)}` (single file persisted for shard-script consumption via `jq`, reflector analysis, and end-of-session summary). Producer-validates after Write via `bash scripts/validate-json.sh hypothesis.schema.json <path>` per Conventions / JSON Schema validation helpers; abort with explicit error on validation failure.
4. Load lessons | Blocked by #3
   - inline task prompt
     - runs `grep-lessons.sh` from hypothesis keywords from previous step
     - runs `update-hit.sh` (lesson hit-tracking) with matched lesson IDs from grep-lessons.sh
5. Trivial task detection -> if trivial, jump to Path 1 | Blocked by #4
   - inline task prompt
     - scout-skip detection: single file, no cross-file deps in hypothesis, no new abstractions
     - trivial detection trades fidelity for latency; if the inline task is uncertain, default to non-trivial
     - returns trivial|non-trivial
   - if trivial: orchestrator writes `.claude-tmp/apex-active/{session}-main-scope.json` inline via the `Write` tool (allowed-files = detected single file + standard safety paths; see Conventions / Scope write producers), then writes the scope-check pointer at `.claude-tmp/apex-active/{session}-scopes/{cc_session_id}.txt` (single line: absolute path to the scope file just written; see Conventions / scope-check hook), then calls p1.md | `~/.claude/skills/apex/p1.md`
   - if non-trivial: TaskCreate below tasks 6. to 9.
6. Scout phase 1 (enumerate -> rank -> screen) against hypothesis
   - Artifacts written to `.claude-tmp/scout/`
   - scout1.md | `~/.claude/skills/apex/scout1.md`
     - TaskCreate (insert before task 7.) the 3 below tasks
       - 6.a enumerate (deterministic enumeration)
         - runs scripts (generates `findings-{session}.json`)
           - Deterministic layers (priority order, each layer optional):
             1. Static imports (project-native parser: madge / pydeps / etc. - explicit dependencies, zero noise)
             2. ast-grep structural queries (tree-sitter, language-aware - call sites, type usages, dynamic imports folded in)
             3. Framework-convention scans (Next.js routes, Rails conventions, etc.)
           - Ripgrep keyword fallback retired in apex 1.x. The fallback used to fire when 0 of the 3 deterministic layers produced any finding; in practice it generated noise (string matches in comments / docstrings / JSON) that propagated through 6.b ranking into expensive 6.c screener cost. The zero-layer case now exits with code 10 immediately and the orchestrator routes to `zero-layer-extract` (proceed-with-prompt-paths) or refine.
             - Noise filter (token-cost contract): two safety nets remain. The deterministic-layer walk skips dot-prefixed dirs (`apps/web/.next`, `apps/api/.turbo`, `.cache`, `.pytest_cache`, `.mypy_cache`, etc.) at any depth, plus an explicit `WORKSPACE_EXCLUDES` set (`node_modules`, `dist`, `build`, `out`, `coverage`, `__pycache__`, `venv`, `target`). After the layer merge, `_enumerate_merge.py` applies a denylist of clearly-not-source paths (lockfiles, sourcemaps, minified, compiled bytecode, archives, fonts, AV, raster images) as a safety net for all layers; dropped count surfaces in `_meta.warnings`. Source-shaped extensions are NEVER in the denylist - the rule is "drop if clearly not human-edited", not an extension allowlist. See `skills/apex/scout1.md` "6.a noise filter" + `_enumerate.py` (`WORKSPACE_EXCLUDES`) + `_enumerate_merge.py` (`NOISE_EXTENSIONS`, `NOISE_BASENAMES`).
           - All script-driven, ground truth list. Layer outputs merged into `findings-{session}.json`:
             - Dedupe by file path, canonicalized via `realpath` (avoids `./foo` vs `foo` vs absolute-path mismatches)
             - Each entry carries `reasons: [{layer: static-imports|ast-grep|framework|lsp|rescout, detail: '...', line_range: [start, end] | null}]` - one item per layer that matched the file; `line_range` populated when the layer reports it (ast-grep, framework, lsp, rescout match locations), null otherwise (static-imports file-level hits). The `lsp` layer queries typescript-language-server / pyright-langserver `workspace/symbol` for identifier-shape seed terms (PascalCase / camelCase / snake_case 3+ chars); silent no-op on TS-less / Python-less repos, protocol failures absorbed into `_meta.warnings` (e.g., `lsp:typescript-language-server:init-timeout-or-error`). The `rescout` layer is reserved for entries merged in by 7.x targeted rescout (see step 7.x); it never appears in the initial 6.a output.
             - Same-layer duplicate reasons collapsed by `detail` string (a single layer reporting the same file twice with the same reason becomes one entry)
             - `confidence: high|medium` derived from layer count (>=3 deterministic layers = high; 1-2 = medium; 4 deterministic max with lsp). With ripgrep retired, the prior `low` value is no longer reachable. The >=3 bar keeps LSP-less repos at `high` when the original 3 fire, and lets typed repos hit `high` with 3-out-of-4. The `rescout` layer is special-cased at 7.x merge time (medium by default; explicit `line_range` promotes to high; see step 7.x) and does not participate in this layer-count formula. Consumed downstream: screener (6.c) biases keep/drop on `medium` (judgment, tilt drop) and `high` (keep unless clear negative); verify (8) treats all mechanically-passing claims as confirmed.
           - Graceful degradation: if some layers unavailable, surviving deterministic layers run.
           - Zero-layer case: if all 4 deterministic layers produce 0 findings, enumerate writes empty `findings-{session}.json` with `_meta.warnings: ['no layers produced findings']` and exits with a sentinel exit code (10) signalling zero-layer to the orchestrator. **Autonomous-vs-question dispatch (smart-default per scout1.md "AskUserQuestion contracts (orchestrator-side)")**: if `hypothesis.discovered_paths` is non-empty AND >=1 path validates on disk, the orchestrator routes through `zero-layer-extract.sh` directly without an AskUserQuestion - the LLM did the discovery work at step 3 and we trust it. The script then PREFERS `discovered_paths` (writing scope with `produced_by="zero-layer-discovered"`) over the regex fallback. ELSE (discovered_paths empty / absent - true blank-slate prompt) the orchestrator surfaces via AskUserQuestion ("no scope detected - hypothesis may need refinement; abort or proceed with prompt-mentioned files only?") and on `proceed-with-prompt-paths` invokes the same script which falls back to regex-extracting `original_prompt` for file path tokens (project-tree-shaped + quoted/backticked) and writes scope with `produced_by="zero-layer-inline"`. Either source: `bash skills/apex/scripts/zero-layer-extract.sh {session}` (single positional arg, reads `$CC_SESSION_ID` from env) validates each candidate on disk, writes `.claude-tmp/apex-active/{session}-main-scope.json` (allowed-files = validated paths + standard safety paths), and writes the scope-check pointer at `.claude-tmp/apex-active/{session}-scopes/{cc_session_id}.txt` (single line: absolute path to the scope file). Script exits 10 only when BOTH sources yield zero validated paths (orchestrator runs the verify-exit-1 abort surface). The pipeline then SKIPS steps 6.b, 6.c, 7, 8, AND 9 (no rank, no screening, no claim verification, no path decision - there are no findings to process and the path is forced to trivial-equivalent Path 1) and the orchestrator calls p1.md directly with NO preflight artifact written (matches the trivial-detection branch at step 5; p1.0 reads an absent preflight and runs the no-findings-consultation branch uniformly across both trivial and zero-layer cases). The orchestrator marks the queued tasks 6.b, 6.c, 7, 8, and 9 as completed (skipped, no-op) before invoking p1.md so the TaskList reflects reality. If both sources yield zero validated file paths, the orchestrator aborts with the same surface as a verify exit-1 (and runs `session-end-hook.sh {session}` inline per "Mid-/apex abort cleanup"). On abort (user choice or cancelled question): orchestrator runs `session-end-hook.sh {session}` inline and exits cleanly. Note: `_enumerate.py:extract_seeds()` ALSO reads `discovered_paths` and merges into `seed_paths` so the deterministic layers (static-imports / framework / lsp) expand from LLM-discovered paths the same way they expand from prompt-explicit paths - in many cases this means the zero-layer case never triggers because the seeded layers find findings.
         - returns `findings-{session}.json` to apex
       - 6.b rank (deterministic ranker + top-K cap) | Blocked by #6.a
         - rank script (`scripts/rank-findings.sh` -> `_rank_findings.py`)
           - reads `findings-{session}.json`
           - scores each entry deterministically: `base (layer-count: 1=0.4, 2=0.7, 3+=1.0; 4 max with lsp) + path-token-overlap-bonus (0..0.3) - size-penalty (0/0.1/0.2 by file LOC)`, clamped to [0, 1]
           - sorts descending by score; applies a top-K cap (default `--top-k 30`)
           - always emits `_meta` telemetry: `findings_count` (pre-filter), `ranked_count` (length of `ranked[]`), `dropped_below_cap`, `deterministic_count`, `min_confidence`, `top_k`
           - optional `--min-confidence medium|high` flag drops findings entries below the threshold BEFORE ranking (default `medium` = no filter; `high` keeps only 3-layer entries)
           - exits **11** when `dropped_below_cap >= top_k` (cap-overshoot signal: hypothesis is too broad). Orchestrator surfaces AskUserQuestion per scout1.md "AskUserQuestion contracts (orchestrator-side)": `refine | proceed-with-prompt-paths (reuse zero-layer-extract.sh; SKIP 6.c/7/8/9 like 6.a zero-layer) | continue (proceed to 6.c with the already-capped top-K)`. The orchestrator MUST surface all options verbatim - collapsing the option set, adding "for direct implementation" framing to `refine`, or re-routing a `refine` choice into inline implementation is a framework violation (see scout1.md "Anti-rule (post-`refine` routing)"). If the user dismisses or cancels the question without picking an option, treat as abort.
           - reads hypothesis from `.claude-tmp/apex-active/{session}-hypothesis.json` (path passed as CLI arg)
           - emits shared screening prompt template with hypothesis injected verbatim (consumed by the single 6.c screener call)
           - generates `screen-plan-{session}.json` with `{ranked: [...], screening_prompt: "..."}`
           - returns `screen-plan-{session}.json` path to apex
       - 6.c screen (single LLM screening call) | Blocked by #6.b
         - spawns one screener subagent reading `screen-plan-{session}.json` (no fan-out, no aggregator - the prior parallel-shard model was retired in apex 1.x; the deterministic ranker at 6.b ordered + capped the input so a single Sonnet pass is sufficient)
         - screener.md | `~/.claude/agents/screener.md` (Sonnet latest subagent)
           - follows the embedded screening prompt: receives the ranked list + hypothesis, returns keep/drop + relevance annotation per file
           - writes structured result directly to `.claude-tmp/scout/screened-{session}.json`: `{kept: [{file, screener_reason, reasons, confidence}], dropped: [{file, screener_reason}]}` where `screener_reason` is the screener's free-text keep/drop justification, and `reasons` + `confidence` are forwarded verbatim from the screener's input ranked entry (the layer-attribution array - same shape as findings.json - and confidence are computed at 6.a and propagate through rank + screen so verify (8) can apply confidence-aware screening on `screened-{session}.json`); schema-validated
           - writes prose claim-provenance trace to `.claude-tmp/apex-active/{session}-traces/entryflow/screener-attempt-N.md` (kept/dropped narrative + one-line reason per drop). N is `1` for the initial 6.c run; if step 8 returns exit-2 and 6.c re-runs, that second pass writes `screener-attempt-2.md` so the first attempt's reasoning is preserved alongside the second.
           - returns the JSON path + one-line status to apex, never the findings body
7. Scout phase 2 preflight -> select medium or complex mode (rescout if gaps) | Blocked by #6
   - scout2.md | `~/.claude/skills/apex/scout2.md`
     - reads `screened-{session}.json` + prompt; LLM judgment generates `MISSED` (JSON-string of missed_regions)
     - calls `scripts/scout2-finalize.sh --session {session} --missed "$MISSED"`: deterministic helper that reads `screened` + `screen-plan`, computes `effective_blast` (`small` if kept-file count <= 15 AND `_meta.findings_count` (pre-rank) <= 30 - i.e., the screen-plan did not need its top-K cap; `large` otherwise - both terms required so wide pre-rank scopes that screening culled to <= 15 still route to large/Path 2), composes + producer-validates `preflight-{session}.json` (`{missed_regions, effective_blast, mode}`), echoes the selected `mode` to stdout

## Failure handling

- `cleanup-session.sh` is idempotent: exit 0 on partial cleanup with warnings written to stderr. Orchestrator never blocked on cleanup. Entry points: success-path steps (p1.5 / p2.6) call `cleanup-session.sh` directly; SessionEnd / mid-abort cleanup goes through `session-end-hook.sh` (which wraps `cleanup-session.sh` plus a hypothesis-file fallback) - the inner `cleanup-session.sh` is shared and idempotent across both entry points. Does NOT touch `{session}-hypothesis.json` - it is consumed downstream by p1.6 / p2.7 inline summary, which cleans it up on success.
- `session-end-hook.sh` (SessionEnd) wraps `cleanup-session.sh` and additionally removes `{session}-hypothesis.json` if still present (belt-and-suspenders fallback when consumer fails). When invoked by Claude Code's SessionEnd hook (no positional arg), it reads `session_id` from the hook's stdin JSON and matches against active manifests' `cc_session_id` / `p2_cc_session_id` to derive the apex session token. When invoked manually with a positional arg (cleanup-stale at step 2, or any orchestrator-driven cleanup), it uses that token directly. Runs on success completion AND on abort / crash. Idempotent. Replaces the prior plain `cleanup-session.sh` SessionEnd invocation so stale manifests do not poison concurrency detection. **Path-2 mid-transition guard**: when the SessionEnd-mode match hits via `cc_session_id` (entry-flow leg) but `p2_cc_session_id` is unset AND `{session}-plan-candidate.json` exists on disk, the hook skips cleanup. The entry-flow Claude Code session ending at the p2.0c context-clear boundary MUST NOT wipe the manifest / scopes / traces / hypothesis that the post-clear `p2.md` session inherits at p2.0 init. The guard fires only on the `cc_session_id` leg; `p2_cc_session_id` matches always proceed (the post-clear session ending is the canonical end-of-Path-2 signal). Path-1 sessions never write `{session}-plan-candidate.json`, so the guard is inert for them. Crashed Path-2 entry-flow sessions that wrote a plan-candidate but never reached p2.0c are caught by the next /apex run's stale-manifest sweep at step 2 (cleanup-stale-and-proceed).
- **Mid-/apex abort cleanup**: any orchestrator exit that bypasses p1.5 / p2.6 (verify exit-1 abort - either `preflight_bad` or `screened_unconverged`; AskUserQuestion-abort at step 2 / step 6.a zero-layer / 6.b / p1.0 / p2.0; zero-layer "no validated paths" abort from step 6.a; teammate-failure abort) should run `session-end-hook.sh {session}` inline before returning, mirroring the explicit p2.0c plan-mode-rejection branch. The Claude Code SessionEnd hook is the catch-all when the entire Claude Code session ends; the inline call handles the "user aborts /apex but stays in the same Claude Code session" case so the manifest does not orphan and trigger false-positive concurrency detection from sibling /apex calls.

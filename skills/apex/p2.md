# p2 (Path 2 chain)

Spec: `apex-core.md` "Path 2 (p2)" | `apex-core-overview.md` "Path 2".

Invoked AFTER the p2.0c context clear. The plan embedded by `planner.md` at p2.0b survives the clear; the plan's first instruction is `read and follow ~/.claude/skills/apex/p2.md`, so this skill is the entry point in the new context.

## p2.0 Initialisation (post-context-clear)

Owns four side effects, then queues p2.1 -> p2.7. Capture the apex `{session}` token from the embedded plan body before any of the steps below; without it every artifact path is wrong.

### Step 1: Capture working-tree baseline

Single producer for all teammate p1.1b polishes. Teammates run `p1.md --teammate` and consume this baseline rather than re-capturing -- avoids races on the shared artifact. Same shape as `p1.0` main-mode (`schemas/baseline.schema.json`).

```
git_head=$(git rev-parse HEAD)
mkdir -p .claude-tmp/apex-active
baseline=".claude-tmp/apex-active/{session}-baseline.json"
PYTHONPATH="$HOME/.claude/skills/apex/scripts" python3 -c "
import sys, json
from _validate import producer_validate, ValidationError
data = {'head_sha': '$git_head'}
try:
    producer_validate(data, 'baseline')
except ValidationError as e:
    print(f'baseline producer-validate failed: {e}', file=sys.stderr)
    sys.exit(1)
with open('$baseline', 'w') as f:
    json.dump(data, f)
"
```

### Step 2: Concurrent-apex conflict check

Same logic as `p1.0` main-mode: enumerate pre-dirty files (tracked-modified UNION untracked-non-ignored) and scan other active apex `*-main-scope.json` files for overlap. Excludes our own `{session}-main-scope.json`.

```
pre_dirty=$( (git diff --name-only HEAD; git ls-files --others --exclude-standard) | sort -u )
overlap=()
for scope in .claude-tmp/apex-active/*-main-scope.json; do
  [[ -f "$scope" ]] || continue
  [[ "$scope" == *"{session}-main-scope.json" ]] && continue
  while IFS= read -r f; do
    [[ -z "$f" ]] && continue
    jq -e --arg f "$f" '.allowed_files | index($f)' "$scope" >/dev/null 2>&1 \
      && overlap+=("$f -> $(basename "$scope")")
  done <<< "$pre_dirty"
done
```

On `${#overlap[@]} -gt 0`:
- AskUserQuestion (header: "Concurrent apex"; options: `abort`, `proceed-anyway`; dismiss/cancel = abort)
- abort -> run `scripts/session-end-hook.sh {session}` inline; exit cleanly
- proceed-anyway -> pre-dirty files are processed normally per "process as normal file" rule (staged, polished, committed alongside apex-introduced edits)

### Step 3: Append `p2_cc_session_id` to the manifest

`p2_cc_session_id` is the current Claude Code session id (post-context-clear). The append PRESERVES every existing field -- `cc_session_id` (entry-flow Claude Code session id) and `pid` (OS pid; `pid` stays valid because Claude Code's context-clear keeps the same OS process) are NEVER overwritten.

```
manifest=".claude-tmp/apex-active/{session}.json"
tmp=$(mktemp)
jq --arg id "$CC_SESSION_ID" '. + {p2_cc_session_id: $id}' "$manifest" > "$tmp" \
  && mv "$tmp" "$manifest"

# Producer-validate the appended manifest (catches malformed jq output at source).
PYTHONPATH="$HOME/.claude/skills/apex/scripts" python3 -c "
import sys, json
from _validate import producer_validate, ValidationError
data = json.load(open('$manifest'))
try:
    producer_validate(data, 'manifest')
except ValidationError as e:
    print(f'manifest producer-validate failed after p2 append: {e}', file=sys.stderr)
    sys.exit(1)
"
```

`$CC_SESSION_ID` is the new Claude Code session id available in the post-context-clear environment. p2.5 reflector reads `p2_cc_session_id` to locate the p2 TaskList at `~/.claude/todos/{p2_cc_session_id}-agent-{p2_cc_session_id}.json`.

### Step 4: Write the scope-check pointer for the post-context-clear session

The entry-flow `cc_session_id` pointer at `{session}-scopes/{cc_session_id}.txt` (written before plan-mode entry) is now orphaned. Without this new pointer, the PreToolUse scope-check hook is pass-through for the post-context-clear session and any subsequent `Edit` / `Write` is unguarded. Both pointers point at the SAME `{session}-main-scope.json` -- p2.6 cleanup wipes the dir wholesale.

```
mkdir -p .claude-tmp/apex-active/{session}-scopes
printf '%s\n' "$(realpath .claude-tmp/apex-active/{session}-main-scope.json)" \
  > .claude-tmp/apex-active/{session}-scopes/$CC_SESSION_ID.txt
```

## p2.2 Shut down teammates

Blocked by p2.1. Pure inline orchestrator action -- no skill. Runs after every surviving teammate has completed (or been formally dropped via the `teammates.md` failure-recovery (c) branch).

`teammates.md` already monitors and coordinates teammates until done; p2.2 begins once `TaskList` shows every teammate's terminal task `completed` (or dropped). The team itself remains active (members are still alive in the `apex-{session}` team) until this step retires them.

### Step 1: Per-teammate ack + shutdown_request

For each teammate still active in the team, send a one-line acknowledgement (resolves the teammate's last idle notification cleanly) then a `shutdown_request`. Teammates respond with `shutdown_response` and exit. Per `SendMessage` docs, originating `shutdown_request` here is explicitly authorised because the teammate's work is complete -- this is not a forced kill.

```
for tid in "${TEAMMATE_IDS[@]}"; do
  # ack final message (plain text)
  SendMessage
    to:      "$tid"
    summary: "ack p2.1 completion"
    message: "Task complete -- shutting down."

  # shutdown_request (structured); teammate replies with shutdown_response (approve=true) and exits
  SendMessage
    to:      "$tid"
    message: {"type": "shutdown_request", "reason": "p2.1 complete"}
done
```

Wait for every `shutdown_response` (or the equivalent post-shutdown idle notification) before proceeding. Replacement teammates (failure-recovery (b)) and survivors are treated identically -- both go through the same loop.

### Step 2: TeamDelete

Once every teammate has shut down (the team has zero active members), call `TeamDelete`. This removes:

- `~/.claude/teams/apex-{session}/` -- team config + member registry
- `~/.claude/tasks/apex-{session}/` -- the shared TaskList created by `TeamCreate` at p2.1

```
TeamDelete
```

`TeamDelete` fails if the team still has active members -- the per-teammate `shutdown_request` loop in Step 1 is mandatory before this call. The team name is resolved from the current session's team context (set by the `TeamCreate` call in `teammates.md` Step 3a).

### Failure-recovery interaction

If a teammate aborted earlier and was formally dropped via `teammates.md` failure-recovery (c) ("continue with surviving teammates"), it never registered as completing its task and was already removed from the team. Skip dropped teammates in the Step 1 loop -- they are not in `TEAMMATE_IDS`.

## p2.3 Verify (lint/build) + fix

Blocked by p2.2. Single central verify pass for the whole p2 session. Teammate `p1.2` is skipped under `--teammate`, so any teammate-introduced breakage is absorbed here into the 3-attempt fix cap.

```
read and follow ~/.claude/skills/apex/verify-fix.md  --phase p2  --session {session}
```

`verify-fix.md` runs `scripts/verify-build.sh` -> spawns `agents/executor.md` per failed attempt, capped at 3 via `{session}-fix-attempts-p2.json` (producer-validated against `schemas/fix-attempts.schema.json`). Trace path: `{session}-traces/p2/fix-{attempt-N}.md`.

### Cap-reached abort path

When `verify-fix.md` exits non-zero (cap reached, build still failing):

1. Surface the contents of `.claude-tmp/apex-active/{session}-verify-errors.txt` to the user (truncate to the last ~50 lines if larger; the full file remains on disk for `cleanup-session.sh` / `session-end-hook.sh` to remove).
2. Run `scripts/session-end-hook.sh {session}` inline (mid-/apex abort cleanup per `shared-guardrails.md`).
3. Skip p2.4 / p2.5 / p2.6 / p2.7 -- the session is over.

This is the ONLY p2.3 mid-abort trigger. A clean verify (`verify-fix.md` exits 0) means the chain proceeds to p2.4 unconditionally.

## p2.4 Tail (learn / documentation / git)

Blocked by p2.3. Central tail for the whole p2 session.

```
read and follow ~/.claude/skills/apex/tail.md  --phase p2  --session {session}
```

`tail.md` runs `scripts/detect-tail-mode.sh` (baseline-pinned size signal) to pick `economy` vs `full`, then dispatches the relevant agents in a single parallel batch (Sonnet, foreground, no traces):

| Mode | Agents spawned |
|------|----------------|
| `economy` (FILE_COUNT <= 3 AND LINE_DELTA <= 50) | `git.md` only |
| `full` | `learn.md` + `documentation.md` + `git.md` |

### Integration pass (p2.4 only)

`documentation.md` at `--phase p2` owns first-write on the planner's `shared_files` list (read from the embedded plan body; excluded from every teammate scope by the disjoint-scope rule at p2.0b). Per-teammate scope-internal doc edits already happened in each teammate's own `p1.3` (`tail.md --phase teammate`); p2.4 is the only place where cross-teammate docs / READMEs are written.

`git.md` at `--phase p2` stages teammate-modified tracked files AND teammate-newly-created untracked files (computed from `(git diff --name-only {baseline.head_sha}; git ls-files --others --exclude-standard) | sort -u`), filters via the dotenv-secret denylist + `git check-ignore`, per-file `git add`, then commits (no push).

### Fail-silent contract

Tail is best-effort. `detect-tail-mode.sh` failure or any agent failure logs to stderr / `~/.claude/tmp/git-agent-errors.log`; the chain proceeds to p2.5. Hard-failing here would block p2.5 / p2.6 / p2.7 for cosmetic gains -- learn / docs / git are commit-time conveniences, not correctness gates.

## p2.5 Self-reflect

Blocked by p2.4. Reflection principle: compare (a) what the session DID -- pipeline executed + tasks completed per end-of-session summary -- against (b) what it SHOULD have done -- pipeline-as-spec + original prompt + hypothesis from `{session}-hypothesis.json` (embeds `original_prompt`). Spot the gaps and what could have been done better.

```
read and follow ~/.claude/skills/apex/reflect.md  --phase p2  --session {session}
```

`reflect.md` runs `scripts/reflect-traces.sh --phase p2` (heuristic-first; appends `## {session} - p2-heuristics - {timestamp}` block to `~/.claude/tmp/apex-workflow-improvements.md` under the shared `flock`), parses `novel_flagged` from the latest matching block, and conditionally spawns `agents/reflector.md` (Haiku, foreground) when `novel_flagged >= 1`. The reflector reads `p2_cc_session_id` from the manifest (written at p2.0 Step 3) to locate the post-context-clear TaskList at `~/.claude/todos/{p2_cc_session_id}-agent-{p2_cc_session_id}.json`; trace inputs are `{session}-traces/p2/*.md` only (entryflow already covered by step 10's reflector). Snapshot file is `/tmp/{session}-p2-snapshot.txt` (caught by p2.6's `/tmp/{session}-*` cleanup glob).

### Fail-silent contract

Reflection is a workflow-improvement signal, not a correctness gate. `reflect-traces.sh` always exits 0; the reflector itself fail-silents to `~/.claude/tmp/reflector-errors.log` and returns success to the orchestrator so p2.6 / p2.7 are NOT blocked.

## p2.6 Clean-up session

Blocked by p2.5. Idempotent wipe of every session-keyed artifact except `{session}-hypothesis.json` (preserved for p2.7).

```
bash $HOME/.claude/skills/apex/scripts/cleanup-session.sh  --session {session}
```

`cleanup-session.sh` removes (per `apex-core.md` p2.6 list): `.claude-tmp/scout/*{session}*` (all scout artifacts), `.claude-tmp/apex-active/{session}-*-scope.json` (main + every teammate scope), `.claude-tmp/apex-active/{session}-scopes/` (all scope-pointer files), `.claude-tmp/apex-active/{session}-*-task.md` (all per-teammate task descriptions), `.claude-tmp/apex-active/{session}-traces/`, `.claude-tmp/apex-active/{session}.json` (manifest), `.claude-tmp/apex-active/{session}-fix-attempts-*.json` (covers `main` and `p2` contexts), `{session}-verify-rerun.json`, `{session}-baseline.json`, `{session}-verify-errors.txt`, `/tmp/{session}-*` (reflector snapshots). Exit 0 on partial cleanup with stderr warnings; the script is best-effort.

`{session}-hypothesis.json` is intentionally NOT cleaned -- p2.7 consumes it. `summary.md` removes it on success; `session-end-hook.sh` is the idempotent fallback when the consumer fails.

`session-end-hook.sh` (which wraps this script) ALSO runs as the SessionEnd hook on abort / crash with the same idempotent contract -- p2.6 is the success path, not the only path.

## p2.7 Inline summary

Blocked by p2.6. Final user-facing message of the session.

```
read and follow ~/.claude/skills/apex/summary.md  --phase p2  --session {session}
```

`summary.md` runs inline on the host model (NOT a subagent -- the output IS the summary). Reads `{session}-hypothesis.json` (preserved by p2.6; consumer-validated against `schemas/hypothesis.schema.json`) and emits three sections in order:

- **Original prompt summary** -- one or two sentences paraphrasing `original_prompt` (no verbatim echo).
- **Hypothesis vs reality** -- compare the orchestrator's working hypothesis against what shipped; surface gaps from working memory (TaskList state, traces, verify outcome). One short bullet per gap, max 3.
- **Short executive summary** -- 3-5 sentences. What was done, what verifications passed, what was committed; reference key files by path.

On success the skill removes `{session}-hypothesis.json`. Soft-error contract: a missing or schema-invalid hypothesis is treated as a one-line user-facing notice and exit 0 -- the chain has already done its work and a hard failure here only confuses the user.

## Mid-abort handling

Any abort path that bypasses p2.6 MUST run `scripts/session-end-hook.sh {session}` inline before exiting. Triggers from p2.0:
- conflict-check AskUserQuestion -> abort (Step 2)
- p2.3 fix-cap reached (3 attempts; surfaced by `verify-fix.md`)
- teammate-failure abort routed through `teammates.md` recovery tree

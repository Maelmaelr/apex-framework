# execute (step 8)

Spec: `apex-core.md` step 8.

## 8.0 Init

- Capture working-tree baseline:
  ```
  bash skills/apex/scripts/apex-baseline.sh
  ```
  Writes `.claude-tmp/apex-active/{session}-baseline.json`: `{head_sha: <git rev-parse HEAD>, pre_dirty: [<repo-relative paths>]}`. Consumed by steps 9 / 11 / 12 / 13. Step 12 excludes `pre_dirty` from staging so user-pre-existing WIP is never bundled into the apex commit.

## 8.1 Pre-flight wc-l split queue

- Run `wc -l` on `{session}-main-scope.json` `allowed_files`. Files > 500 LOC always split. Files > 400 LOC queue a split task ahead of normal edits unless the file is continuous-prose (`*.md` heuristic + author judgement).
- The `file-health-hook.sh` PreToolUse hook is the safety net for files that grow during execution (blocks `Edit` / `Write` on > 500 LOC files).
- **i18n large-locale routine hint**: a locale message file (`messages/*.json`, `locales/**`, `i18n/**`) over ~500 LOC cannot be `chunk-scope`-split (it is one file) and the file-health gate will block in-place growth. When a task adds/changes keys in such a file, the spawn prompt carries `"<locale-file> exceeds the file-health ceiling: apply key changes in pre-chunked batches of <=8 keys per Edit, and mirror the SAME key set across EVERY locale file in the dir (i18n completeness)"` as a routine dispatch hint - not a reactive mid-edit split discovered by the executor. Reflector ad37c6d1: 4058-line locale files forced the executor to reactively split i18n edits into <=8-key chunks every locale-touching session; pre-chunking upfront removes the recurring friction.

## 8.2 Task split + disjoint scopes (goals-driven)

- **`hypothesis.goals.length == 1`** (single-task / fix-bug-in-file-Y prompts): 1 executor task spanning the full scope. Spawn prompt carries the single goal verbatim. Behaviour identical to the prior default; the goal text is now structured rather than implicit in the hypothesis prose.
- **`hypothesis.goals.length > 1`** (multi-task / audit prompts): N executor tasks, one goal per spawn prompt. Per-task `allowed_files` is the subset of `{session}-main-scope.json` `allowed_files` whose paths match the goal's nouns. Compute by cheap grep: tokenize each goal (lowercase, drop stopwords + tokens <4 chars - same recipe as discoverer keyword extraction), then intersect main-scope paths with `grep -li <token>` hits. A goal whose noun-set yields no scope intersection inherits the full main-scope (degenerate fallback; logged in trace).
- **Goals with overlapping `allowed_files` OR shared exported symbols across per-task scopes** are serialized into a single follow-up task per the existing cross-task touch-points rule, so pairwise-disjoint validation continues to hold for the parallel set. Symbol-overlap check is a cheap grep over per-task `allowed_files`: when an `export const`/`export function`/`export default` declared in task A's files is referenced (`import .* from '<base>'`) by task B's files, merge the two into one serialized task. Reflector 213c1afc surfaced the gap: seedance exports spanned task A/B boundary, executor B reported `implemented` while the consuming file in another scope still referenced the renamed symbol; cross-task export overlap masquerades as goal-scope-mismatch at step-15 audit.
- **Concerns-aware pre-split (B0)**: before the scope-size hard split (B1), inspect each per-task goal text for enumerated concerns (rough heuristic: count `+`/`,`/` and ` separators and numbered/lettered list markers). A goal that names 4+ enumerated concerns OR whose per-task `allowed_files` count is >=5 with high coupling (shared parent dir + shared imports) is a candidate for re-decomposition: re-enter step 4 to refine `goals[]` into N concern-level goals OR pre-split the task at the hypothesis level. Reflector cluster 94000169 / 213c1afc / 95d6e4f1 / d2564b0f: executor `tool_calls_made >= 50` consistently rolls out of unsplit multi-concern goals; the executor-side E2 budget hint catches it post-hoc, but pre-split is cheaper than a `split-needed` redispatch.
- When 2+ tasks are spawned (regardless of goals.length), validate per-task `allowed_files` via:
  ```
  python3 skills/apex/scripts/validate-disjoint-scopes.py <plan-json>
  ```
  - per-task `allowed_files` pairwise disjoint (excluding standard safety paths)
  - union is a subset of `{session}-main-scope.json` `allowed_files`
- Cross-task touch points are routed to a serialised follow-up task (no parallel write conflict).
- **Idempotency**: re-running the same prompt produces the same `goals[]` (deterministic from the user-prompt + the step-1/4 prompt-template hint), therefore the same N tasks. If the prior run achieved the goals, each executor returns `already-satisfied` (see `agents/executor.md`); nothing is staged at step 12 -> empty-diff path skips the commit.
- **Scope-size hard split (B1)**: after the goals-driven split, for any executor task whose per-task `allowed_files` count exceeds 8, hard-split via `python3 skills/apex/scripts/chunk-scope.py -n 2` (one path per stdin line). The original task is replaced by 2 sub-tasks; goal text duplicates across both. The chunker keeps directory-siblings together; the resulting `allowed_files` sets are pairwise disjoint by construction so the disjoint-scopes validation continues to hold. First executor to implement wins; the second sees `already-satisfied`.
- **Coupled-merge sequential ceiling (B2)**: B1's parallel chunk-split is forbidden for tasks merged by the coupling rule above (overlapping `allowed_files` / shared exported symbols) or by `apex-core.md` 8.2 collapse / same-domain-noun serialization - coupling needs one consistent author, so a parallel split would race the shared contract. But a coupled-merged task is NOT exempt from a size ceiling: when the merged task's union `allowed_files` count is >12 OR its joined goal carries 3+ enumerated concerns, decompose into a SEQUENTIAL shared-spec chain instead of dispatching one unbounded executor - task 1 authors the canonical spec/module the concerns share; tasks 2..N each consume that spec read-only in a fresh context, one concern-layer each, handed task 1's `git diff` AND a short verified-sections snapshot (the 5-10 files T1 read deepest, each with a one-line "sections already confirmed correct, do not re-audit" note) as input, so T2..N do not re-read and re-audit the large shared files T1 already validated (reflector 177cea68 / 2f253b91: T2/T3 each re-read the same large spec files independently, ~3x redundant reads, because no inter-task confirmation handoff existed - only the git diff was passed). Coupling forbids PARALLEL split, never SEQUENTIAL. **This ceiling is a hard pre-dispatch assertion, not an after-the-fact judgement**: immediately before spawning ANY collapsed / coupled-merged / serialized task, the orchestrator MUST evaluate `union(allowed_files) <= 12 AND enumerated_concerns < 3 AND no estimate-then-reconcile / compute-then-refund / Phase-1+Phase-2 phase-pair shape (two temporally-ordered sub-phases over one shared contract) AND projected_context < ~150k tokens`; on failure the SEQUENTIAL shared-spec decomposition is mandatory and dispatching the merged task as one executor is a contract violation (the rule reads "decompose", not "may decompose"). The phase-pair / token-projection clauses catch the 2-phase task that slips the file/concern gates yet still blows the E1 ceiling (reflector c4b6d57b: Scenario B Phase-1 estimate + Phase-2 reconcile, 4 files / 2 concerns, 171k tokens, status split-needed, self-report 41 vs actual 65 tool_uses). Reflector fa269898 (user-flagged x2): a 3-concern / 46-file coupled merge ran one 134-tool-use / 256k-token / ~20min executor because the merge rule had no ceiling and silently defeated B0 (3+ concerns) and B1 (>8 files); reflector cluster c2545ab8 / a7fdec08 / aff908d5 / dac6d67e: merged dispatches kept crossing E1 (files=21>12, tool_calls=78>50) because the ceiling was applied reactively rather than asserted at the spawn site.

- **Read-only audit goal-cluster (B3)**: when a multi-goal task is pure read-only (mode `report-only`, OR every goal is a verify / check / audit with no write target) the B2 shared-spec author step does not apply - there is no spec to author. Do NOT dispatch one agent over all goals (a flat 10-goal audit ran 57 tool_uses / 311k tokens, ~2x the E1 ceiling - reflector a64f4fd9) and do NOT fan out 1-agent-per-goal (re-reads the shared surface N times). Partition the goals into 2-3 balanced clusters (~3-4 goals each, grouped by shared file surface) and dispatch ONE read-only executor per cluster, each handed only its cluster's scope subset - every dispatch stays under the 50 tool_use / 150k token E1 ceiling while audit fidelity is preserved (reflector a64f4fd9, 68ccbfe5).

## 8.3 Dispatch

Per task:

- Spawn `agents/executor.md` (Sonnet if `tier=economy`; main session model if `tier=standard`; the tier was decided at step 7).
- **Parallel dispatch (mandatory when N >= 2 tasks)**: spawn all N executor Agent calls in ONE assistant message AS multiple tool_use blocks AND set `run_in_background: true` on each - foreground multi-block alone serialises (orchestrator one-spawn-per-message drift; even single-message foreground siblings get ordered), so `run_in_background` is the actual concurrency primitive. The orchestrator yields the turn and the harness re-invokes it as each executor completes; dispatch-summary.json accumulates in arrival order and step 9 starts only after all N return. Sequential dispatch is legitimate ONLY for coupled / B2 sequential shared-spec chain tasks - never for the goals-driven N-task parallel set in 8.2 (user-flagged + reflector e1827632: bug1+bug2 dispatched one-per-message serially despite disjoint scopes, parallel only after user intervention).
- **Spawn-prompt context (executor stack)** - explicit, not inherited:
  - hypothesis (verbatim)
  - `goal` - the task's `hypothesis.goals[]` entry as a **condensed key-term label** (<=6 terms via the step-6 deterministic recipe: lowercase, drop stopwords + <4-char tokens; e.g. `"onboarding stuck-redirect session"` not the 16-34 word clause). One task per goal under `goals.length > 1`; the single goal under `goals.length == 1`. Do NOT restate the verbatim clause in the spawn prompt - it duplicates `hypothesis` (carried verbatim above) and lives in `{session}-hypothesis.json` for step 15's user-facing per-goal list; the executor echoes this label back in its return so `dispatch-summary.json` stays compact too. The label MUST NOT enumerate file paths either - paths already live in `hypothesis.discovered_paths` and the per-task `allowed_files` scope; dereference them via that scope rather than re-inlining a path list in goal text. Reflector cluster ce72570d / f218909a / 6a103a25 / 0a742137 / 716befea / 6aa28b2d: spawn-prompt + dispatch-summary goal echo restated the full clause every spawn; reflector b2716ff4 / 35b42f2b / 177cea68 / 2f253b91: goal strings re-enumerated paths already captured in discovered_paths/scope.
  - per-task scope (`allowed_files` subset)
  - **scope budget hint (E2)**: one-line `"Expected scope: <N> files, ~<K> LOC. If you exceed 2x (>2N files OR >2K LOC) OR ~60 tool calls OR you sense >~150k tokens of your own context, stop and return split-needed."` Compute K via `wc -l` on the per-task `allowed_files`. The tool-use / token clause catches deep-iteration executors on few files that never trip the file/LOC 2x guard (reflector fa269898 user-flagged: 134 tool_uses / 256k tokens on a 46-file merge that the file/LOC guard alone did not stop). **Split-risk pre-extract clause**: when any per-task `allowed_file` is >400 LOC (cheap `wc -l` precheck) OR holds a function at/near the ~20 cognitive-complexity warn-as-error ceiling, append `"<path> is at the file-health / complexity ceiling: extract a helper BEFORE adding field-reads or branches so the edit does not trip verify; budget +5 tool calls for the split."` to the hint. Lifts the split out of a reactive verify-loop fix into a planned first-pass move and stops the file-health split overhead from silently pushing the executor past the E1 ceiling (reflector a7fdec08: apps/web `classify` fn ~20cc tripped verify after field-reads were added in place; aff908d5: file-health split of a >400 LOC spec added an uncounted Read+Write cycle that crossed 50 tool_calls).
  - step 5 lessons hits relevant to the task
  - project-context paths
  - one-line task description
  - trace path: `.claude-tmp/apex-active/{session}-traces/execute/executor-{task-id}.md`
  - **shared read-only preamble (E3)**: when a path appears in >=2 per-task `allowed_files` AND no per-task goal names it as a write target, surface it ONCE per spawn prompt as `"Shared read-only context (do not write): <paths>"` rather than restating the underlying contracts (project specs, parser definitions, seeder defaults, param_exclusions, per-tier pricing rows) inside each per-task goal. Reflector cluster bfffacf9 / fc9f8427 / 95fb28c6: 4-batch executor dispatch consumed 23%+ of per-executor budget on contracts restated across N goals. **Single-task reference-only (E3.1)**: the same rule applies WITHIN one task (not only across 2+ tasks) - any path in this task's `allowed_files` that the task goal's deterministic noun set does not match is reference-only / parity-mirror for this dispatch; surface it under the same `"Shared read-only context (do not write): <paths>"` line and let the executor Read it on demand, rather than the orchestrator pre-loading its full file content into the spawn prompt. Reflector ad37c6d1 / a7fdec08 / aff908d5 / c2545ab8: discovery passed 14-50 `discovered_paths` verbatim into single-task executor context where pure-parity-reference / unchanged-mirror files (settings-client, use-param-exclusions, API resolver mirrors) cost ~2-4k tokens/run as full reads when a path note plus on-demand Read would suffice.
- The executor respects file-health + scope-check PreToolUse hooks.
- The executor returns `{goal, status, notes, tool_calls_made, files_touched: ["<paths>"]}` where status is `implemented` | `already-satisfied` | `failed` | `split-needed`. `files_touched` is the actual list of repo-relative paths the executor wrote, used by the orchestrator to audit against `allowed_files`. Collect per-goal returns in a session-local map for step 15's per-goal summary.
- **Work-produced commands**: the executor runs the setup commands the change produces (deps installs, migrations, seeders, codegen, schema / route / asset regen - an open class, not a closed list) as part of `implemented`; only destructive / prod / credential-gated commands come back `MANUAL:`-prefixed in `notes` for step 15. The orchestrator does NOT relay these back to the user as a manual checklist (see `agents/executor.md` behavior 1).
- **Dispatch self-report log (E1)**: immediately after EVERY executor Agent return (or no-spawn decision), the orchestrator MUST append ONE entry to `.claude-tmp/apex-active/{session}-traces/execute/dispatch-summary.json` (JSON array; append-and-rewrite) carrying BOTH the self-reported fields AND the orchestrator-measured actuals from the Agent tool result. Minimum entry shape - all keys MANDATORY, no exceptions for first-try-clean / economy single-dispatch / all-already-satisfied / no-spawn paths:
  ```
  {"goal": "<echoed label>", "status": "implemented|already-satisfied|failed|split-needed|no-spawn",
   "notes": "<one-line>", "tool_calls_made": <self-report>, "files_touched": ["<self-report>"],
   "tool_uses": <Agent result>, "total_tokens": <Agent result>, "duration_ms": <Agent result>,
   "git_files_touched": ["<git diff --name-only {baseline.head_sha} ∩ task scope>"]}
  ```
  Omitting `tool_uses` / `total_tokens` / `duration_ms` silently disables step-13 reflector's oversized-dispatch + token-ceiling trips on exactly the low-friction runs where no fix-loop forces the data to surface (recurring 9-session compliance gap: 76dc994d/5ec98cfc/500d3e85/94bc1b7f/51b2f54a/525e97be/b512525e/a10cfe1e/093978c0). Self-report alone is gameable: reflector fa269898 saw self-report 71 `tool_calls_made` vs actual 134 `tool_uses` / 256k `total_tokens` (~2x); 145df100 / da97c3c1 saw self-reported `files_touched` under-report the git diff. Reflector keys its trip on the actuals + `git_files_touched`, never on `tool_calls_made` / `files_touched` alone. **ASSERT post-append**: when `status != "no-spawn"`, both `tool_uses` AND `total_tokens` MUST be > 0; a 0 / null / absent value means the Agent return object was not read, NOT that the executor used zero - STOP and re-extract from the Agent tool result before continuing (do not write a placeholder; do not advance to step 13 with the placeholder in place). Recurring 7-session continuation gap post the 9-session original: 169315a7/5f9bdc44/494203ff/7e72ac14/23c32b7e/7e0abf6a/fd09e42c, each surfaced the same `tool_uses=None tokens=None` shape in dispatch-summary entries with non-zero `tool_calls_made` - the spec was descriptive, not prescriptive, and the gap persisted.
- **No-spawn sentinel (E1.1)**: when the orchestrator legitimately bypasses dispatch for a goal (e.g., economy-tier inline judgement that the goal is already satisfied without an executor read pass; or a high-confidence single-Edit slice the orchestrator owns directly), append ONE sentinel entry per skipped goal to the same `dispatch-summary.json`: `{goal, status: "no-spawn", notes: "<one-line reason>", tool_calls_made: 0, files_touched: []}`. Distinct from `already-satisfied` (which is the executor's verdict after a read pass). Without this sentinel the file is absent for the whole step and reflector / apex-improve cannot tell "intentional skip" from "orchestrator forgot to dispatch" (reflector cluster ee81f7b0 + 3d01b930 + fe233cc4: dispatch-summary.json absent on zero-call success paths). The dispatch-only constraint below still forbids inline `Edit` / `Write` / `MultiEdit` / `NotebookEdit` of scope files at step 8 - sentinel covers the legitimate read-only judgement path, not slice writes.
- **Split-needed redispatch (C1 follow-up)**: on `status: split-needed`, the orchestrator re-spawns ONE follow-up executor with `goal = residual_goal` and `allowed_files = residual_files` (cap 1 redispatch per goal). The follow-up spawn carries **delta-only context** - dispatch-1's `what_i_did` + the `git diff --name-only {baseline.head_sha}` of files it already changed + the residual notes - NOT a fresh re-propagation of the full scope; the executor then reads only the `residual_files` it has not already touched, so an already-large dispatch-1 (sensed >~150k tokens) does not pay a second full-scope read (reflector d5f0cc89). If the follow-up also returns `split-needed`, mark the goal `failed` for step 15 with notes `"split-needed twice; residual: <residual_goal>"`. Per-redispatch return is also appended to dispatch-summary.json.
- On failure or split decision, the executor writes a structured trace before returning (see `agents/executor.md`).

## Dispatch-only constraint

The orchestrator MUST NOT inline `Edit` / `Write` / `MultiEdit` / `NotebookEdit` against scope files at step 8. Slice writes belong to executor subagents. Inline writes outside the scope (e.g., `.claude-tmp/` artifacts) remain allowed via the standard safety-path set.

Under `report-only` mode no executor is dispatched at all (step 1 contract); the orchestrator synthesizes the deliverable inline and MUST write `{session}-traces/report-only-findings.md` (classification table / ETL output) plus a `no-spawn` sentinel per goal, so the run is auditable beyond the dispatch-summary `notes` field and the declared `*-audit.md` / `*-report.md` deliverable lands within the step-1 pre-seeded scope (reflector 5ec98cfc, 33935c17).

## Output

- `{session}-baseline.json` (from 8.0)
- Per-task trace files (only on failure or split)
- Modified scope files (touched-by-executor set; consumed by step 9 polish via `git diff` against `baseline.head_sha`)

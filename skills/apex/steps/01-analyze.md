## Contract

Inline. AskUserQuestion if ambiguous; abort = clean exit (no manifest yet, skip session-end-hook). Read `<project-root>/docs/project-context.md` (best-effort; absent = silent skip; cached for downstream; cap read at ~200 lines). When formulating the working interpretation, expect step 4 to emit a `goals[]` decomposition: single-task prompts -> one goal; multi-task / audit prompts ("make sure all X are properly Y") -> N enumerated goals. Internal bias only; no user-visible change at step 1.
   - **Early scope narrowing.** When the original prompt implies a multi-phase plan (>3 implied phases, OR >5 enumerated subtasks, OR explicit phase / step / roadmap language, OR architectural-refactor verbs that predictably touch `docs/architecture/**` / `CLAUDE.md` - rate-limit, middleware, schema-migration, breaking-API, env-var addition, new-locale registration - OR feature work that modifies documented UI / behavior, predictably touching `CLAUDE.md` / `docs/features/**` / `.claude/rules/**`), AskUserQuestion BEFORE step 4 to narrow scope (`audit-only` | `phase-1-only` | `full-scope` | `code-only-no-docs` | `let-me-respec`); do NOT defer to a step 8 re-conversation after goals are drafted ("Step 8 scope re-conversation happened late; pre-run conversation could surface this earlier"). Cheaper to narrow once at step 1 than to discard a 6-goal hypothesis at step 8. The `code-only-no-docs` option pre-coordinates the full doc-touch surface so `docs/**` + `CLAUDE.md` + `.claude/rules/**` edits enter `allowed_files` up-front rather than surfacing post-dispatch as scope drift - the step-11 documentation agent then needs no mid-tail `allowed_files` expansion and step-12 git-stage no longer strands legitimate doc edits (docs/**/*.md + CLAUDE.md + .claude/rules/*.md recurrently appended outside `allowed_files`). For `continue:<plan-file>` prompts specifically, BEFORE the AskUserQuestion read the plan's File Scope section (grep the plan file for `^## (File Scope|Files|Files in scope|Scope)` heading, take the bullet list under it) and pre-populate every doc path it names into the option set so the plan-declared cross-ref docs reach `allowed_files` up-front rather than landing as reactive step-11 doc-agent expand (both plan-file File Scope sections named the docs explicitly).
   - **Review-only hypothesis-shape.** When the prompt names review / audit / check / verify verbs WITHOUT explicit edit verbs ("review my X", "audit Y", "check Z is correctly used"), tag the working interpretation `review-only` and AskUserQuestion to disambiguate intent (`report-only` | `edit-to-fix-found` | `edit-only-if-asked`). Default to `report-only` on dismiss. The chosen mode threads through step 4 hypothesis (carry `mode` field) and step 8 (skip executor entirely under `report-only`; gated executor under `edit-only-if-asked`). "review-only workflows need upfront clarification". **Test-triage variant**: the SAME gate ALSO fires when `original_prompt` matches `/\b((fix\s+(failing\s+)?(tests?|specs?))|(tests?|specs?)\s+(are\s+)?(failing|broken))\b/i` (the test-triage prompt shape uses an edit verb but the actual deliverable is often a triage report not source fixes), offering (`report-only` | `edit-to-fix-found`; dismiss = report-only) BEFORE discovery so plan-only is a first-class option rather than a mid-step-7 redirect after lessons + discovery already ran ("fix failing tests" required mid-flow shape change to report-only after discovery completed). Under `report-only`, pre-seed the declared deliverable output path named in `original_prompt` (`*-audit.md` / `*-report.md` / `*-findings.md`) into `allowed_files` at scope-finalization (mirrors `code-only-no-docs` pre-coordination so the scope-check hook does not block the deliverable write), and emit a lightweight `{session}-traces/report-only-findings.md` capturing the classification / ETL output so the run is auditable beyond the dispatch-summary `notes` field.
   - **Deploy-doc preload.** When `original_prompt` names deploy / wiring verbs (`deploy`, `docker-compose`, `migrate`, `seed`, `sidecar`, `wire`, `wiring`, `integration`), additionally read `<project-root>/docs/integration.md` (or `docs/deploy.md` / `DEPLOY.md` / `INSTALL.md` - first hit wins; best-effort; absent = silent skip; cap ~200 lines) before step 4 hypothesis emission. Closes the gap where hypothesis drafts against assumed-unwired components when the deploy chain is already wired (seeder hypothesis assumed unwired but migrate sidecar already ran db:seed + litellm:ingest; the gap surfaced only at step 8 audit).
   - **Mid-conversation switch-verb gate.** When `original_prompt` is itself a switch verb (`enter apex mode`, `switch to apex`, `go apex on this`, `do this in apex`) rather than a fresh task description, the prior chat turn is investigation context only and is NOT the session's original_prompt. AskUserQuestion (`use-last-task-statement | enter-new-prompt | abort`; dismiss = abort); on `use-last-task-statement` the user picks which prior turn becomes `original_prompt`. Closes the ambiguous step-1 boundary where investigation context bled into an ad-hoc session.
   - **Plan-completed early-exit.** When `original_prompt` is a `continue: <plan-file>` whose top-level goals are all `[x]` / DONE, AskUserQuestion BEFORE step 2 (`close-plan-nothing-to-do` | `narrow-to-explicitly-deferred-items` | `re-spec`; dismiss = close, clean exit, no manifest). For a stale-looking plan status section, run the plan's encoded acceptance tests as the satisfiability proof - field-presence is insufficient. Fixes the continue-form prompt-hash non-convergence the step-13 guard otherwise catches only post-hoc.

# apex step 8 - Execute (full contract)

## 8.0 Init

- Resolve the per-session `diff_anchor` from the manifest's `base_branch`:
  ```
  BASE_BRANCH=$(jq -r .base_branch .claude-tmp/apex-active/{session}.json)
  DIFF_ANCHOR=$(git merge-base "$BASE_BRANCH" HEAD)
  ```
  The apex/<session> fork point, stable from mint through step 15. Propagated in every downstream spawn-prompt (steps 9 / 10.5 / 11 / 13); steps 12 / verify-tests.sh compute it inline from the manifest. Worktree clean at mint by construction - no `pre_dirty` exclusion at step 12 staging.

## 8.1 Pre-flight wc-l split queue

- Run `wc -l` on `{session}-main-scope.json` `allowed_files`. Files > 500 LOC always split. Files > 400 LOC queue a split task ahead of normal edits unless continuous-prose (`*.md` heuristic + author judgement).
- The `file-health-hook.sh` PreToolUse hook is the safety net for files that grow during execution (blocks `Edit` / `Write` when the file is > 400 LOC AND the change adds > 10 net lines; trivial <= 10-line edits pass even on > 500-LOC files).
- **i18n large-locale routine hint**: a locale message file (`messages/*.json`, `locales/**`, `i18n/**`) over ~500 LOC cannot be `chunk-scope`-split (one file) and the file-health gate blocks in-place growth. When a task adds/changes keys there, the spawn prompt carries `"<locale-file> exceeds the file-health ceiling: apply key changes in pre-chunked batches of <=8 keys per Edit, and mirror the SAME key set across EVERY locale file in the dir (i18n completeness)"` as a routine dispatch hint, not a reactive mid-edit split.

## 8.2 Task split + disjoint scopes (goals-driven)

- **`hypothesis.goals.length == 1`** (single-task / fix-bug-in-file-Y prompts): 1 executor task spanning the full scope, single goal verbatim.
- **`hypothesis.goals.length > 1`** (multi-task / audit prompts): N executor tasks, one goal per spawn prompt. Per-task `allowed_files` is the subset of main-scope `allowed_files` whose paths match the goal's nouns. Compute by cheap grep: tokenize each goal (lowercase, drop stopwords + tokens <4 chars - same recipe as discoverer keyword extraction), intersect main-scope paths with `grep -li <token>` hits. A goal whose noun-set yields no intersection inherits the full main-scope (degenerate fallback; logged in trace).
- **Goals with overlapping `allowed_files` OR shared exported symbols across per-task scopes** serialize into a single follow-up task per the cross-task touch-points rule, so pairwise-disjoint validation still holds for the parallel set. Symbol-overlap check is a cheap grep over per-task `allowed_files`: when an `export const`/`export function`/`export default` in task A's files is referenced (`import .* from '<base>'`) by task B's files, merge the two into one serialized task.
- **Concerns-aware pre-split (B0)**: before the B1 hard split, inspect each goal text for enumerated concerns (count `+`/`,`/` and ` separators and numbered/lettered list markers). A goal naming 4+ enumerated concerns OR whose per-task `allowed_files` count is >=5 with high coupling (shared parent dir + shared imports) is a re-decomposition candidate: re-enter step 4 to refine `goals[]` into N concern-level goals OR pre-split at the hypothesis level.
- When 2+ tasks are spawned (regardless of goals.length), validate per-task `allowed_files` via:
  ```
  python3 skills/apex/scripts/validate-disjoint-scopes.py --plan <plan-json> --main-scope <main-scope-json>
  ```
  - per-task `allowed_files` pairwise disjoint (excluding standard safety paths)
  - union is a subset of `{session}-main-scope.json` `allowed_files`
  - every file a `hypothesis.goals[]` entry explicitly names appears in at least one task's `allowed_files` - a goal-named file in no task scope is a plan defect (missed-goal-scope); fix the split before dispatch, never rely on step-11 to catch it
- Cross-task touch points route to a serialised follow-up task (no parallel write conflict).
- **Shared-contract / barrel-file owner**: any shared-contract or barrel file (an `index.ts` re-export, a shared types module) touched by 2+ goals gets an **explicit owner sub-goal** so it is not left as a cross-task gap.
- **Idempotency**: re-running the same prompt produces the same `goals[]` (deterministic from the user-prompt + step-1/4 prompt-template hint), so the same N tasks. If the prior run achieved them, each executor returns `already-satisfied` (see `agents/executor.md`); nothing is staged at step 12 -> empty-diff path skips the commit.
- **Plan-status / doc-only goal routing (B0.5)**: before B1, classify each goal. A goal is plan-status / doc-only when its write target is (a) one plan / status / changelog file under `<project-root>/docs/**`, `<project-root>/plans/**`, `<project-root>/.claude/**`, or a basename match against `**/plan*.md` / `**/status*.md` / `**/changelog*.md`, AND (b) the goal uses doc-update verbs only (`mark`, `update status`, `record`, `note`, `append`) without `implement` / `fix` / `add` / `refactor` / `rename` against any code path. Drop these from the executor dispatch set; append to a queued list consumed by step 11's `documentation.md` tail spawn. Write a dispatch-summary `no-spawn` sentinel per routed goal so the audit trail preserves the decision.
- **Proactive decomposition scout (B0.7; `tier==standard` only)**: BETWEEN the goals-driven split and B1, for each surviving task that is (a) NOT coupled / collapsed / B2-serialized AND (b) has `allowed_files` count ~3-8 (below B1's >8), OR carries `hypothesis.complexity_hint == "high"`, OR is a high-cost large set (count >8 AND an audit/verify verb OR 3+ goal facets OR ~120k projected tokens - this clause lifts the <=8 ceiling), spawn ONE read-only `agents/scout.md` per task, hard-budgeted ~15 tool calls. The scout reads the goal (verbatim clause) + resolved scope and returns a schema-validated sub-task DAG `{subtasks:[{label, files[], depends_on:[idx]}], indivisible, reason}` (producer-validated against `skills/apex/schemas/subtask-plan.schema.json`). Dispatch off the DAG deterministically: `indivisible:true` -> dispatch the goal whole; else REPLACE the task with one small executor per `subtasks[]` entry, joining the 8.3 parallel set (independent sub-tasks fan out via `run_in_background`; `depends_on` chains serialize after their referenced sub-tasks, re-validated by `validate-disjoint-scopes.py`). The scout can only ADD splits - each `subtasks[].files` MUST be a subset of the task's `allowed_files`, never widening scope or merging goals - and its advisory `estimate` MUST NOT gate dispatch (dispatch off `subtasks[]` / `indivisible` only). Scouts run in parallel. Economy / trivial tiers skip the scout.
- **Scope-size hard split (B1)**: after the goals-driven split, for any task whose `allowed_files` count exceeds 8, hard-split via `python3 skills/apex/scripts/chunk-scope.py -n 2` (one path per stdin line). The original task is replaced by 2 sub-tasks; goal text duplicates across both. The chunker keeps directory-siblings together; resulting `allowed_files` sets are pairwise disjoint by construction so disjoint-scopes validation holds. First executor to implement wins; the second sees `already-satisfied`. **B1 exception**: skip the hard split when all goals reduce to ONE atomic semantic change threaded across many low-per-file-complexity files (a single enum / type / signature / key propagated) - mechanical chunking yields intermediate non-compiling dispatch states that fail the in-between verify; keep the task whole past the 8-file ceiling.
- **Goal-coupling vocabulary** (consumed by B2 below + the step-13 reflector): **collapse** = 2+ goals sharing the same parameter / config surface (shared constant, seeder file, or schema definition) AND scope intersection >=50% MAY merge into one executor task carrying the joined goal text + union scope (`deviation_note: "interlocked: <one-line>"`); forbidden when the goals are independent (disjoint scope) or intersection <50%. **same-domain-noun** = 2+ goals referencing the same dominant domain noun (a token surviving the deterministic stopword / min-length filter and appearing in 2+ goal strings) are intent-coupled even with disjoint grep-level `allowed_files`; serialize them pre-dispatch as one follow-up task (never parallel + redispatch). **no self-validation** = each executor does one thing for one goal, no same-context second pass over its own work - errors are caught by step-10 verify and cross-goal correctness defers to a future context-isolated validator.
- **Coupled-merge sequential ceiling (B2)**: B1's parallel chunk-split is forbidden for tasks merged by the coupling rule above (overlapping `allowed_files` / shared exported symbols) or by the goal-coupling vocabulary (collapse / same-domain-noun, defined in the bullet above) - coupling needs one author. But a coupled-merged task is NOT size-exempt: when its union `allowed_files` count is >12 OR its joined goal carries 3+ enumerated concerns, decompose into a SEQUENTIAL shared-spec chain, not one unbounded executor - task 1 authors the canonical spec/module the concerns share; tasks 2..N each consume it read-only in a fresh context, one concern-layer each, handed T1's `git diff` AND a verified-sections snapshot (the 5-10 files T1 read deepest, each with a one-line "confirmed correct, do not re-audit" note). **A hard pre-dispatch assertion, not after-the-fact judgement**: before spawning ANY collapsed / coupled-merged / serialized task, the orchestrator MUST evaluate `union(allowed_files) <= 12 AND enumerated_concerns < 3 AND no estimate-then-reconcile / compute-then-refund / Phase-1+Phase-2 phase-pair shape (two temporally-ordered sub-phases over one shared contract) AND projected_context < ~150k tokens AND NOT (union(allowed_files) > 8 AND predicted_tool_calls > 25)`; on failure the SEQUENTIAL decomposition is mandatory and dispatching the merged task as one executor is a contract violation ("decompose", not "may decompose").

- **Read-only audit goal-cluster (B3)**: when a multi-goal task is pure read-only (mode `report-only`, OR every goal is a verify / check / audit with no write target) the B2 shared-spec author step does not apply. Do NOT dispatch one agent over all goals and do NOT fan out 1-agent-per-goal. Partition the goals into 2-3 balanced clusters (~3-4 goals each, grouped by shared file surface) and dispatch ONE read-only executor per cluster, each handed only its cluster's scope subset - every dispatch stays under the 50 tool_use / 150k token E1 ceiling.

## 8.3 Dispatch

Per task:

- Spawn `agents/executor.md` (model `sonnet` if `tier=economy`; model `opus` if `tier=standard`; tier decided at step 7). Pass the model explicitly on every dispatch Agent call - executors never inherit the main session model.
- **Parallel dispatch (mandatory when N >= 2 tasks)**: spawn all N executor Agent calls in ONE assistant message AS multiple tool_use blocks AND set `run_in_background: true` on each - foreground multi-block alone serialises, so `run_in_background` is the actual concurrency primitive. The orchestrator yields the turn and the harness re-invokes it as each executor completes; dispatch-summary.json accumulates in arrival order and step 9 starts only after all N return. **No fallback wakeup**: after yielding, do NOT `ScheduleWakeup` a hang-guard for the in-flight executors - the harness auto-re-invocation above IS the wake mechanism. Sequential dispatch is legitimate ONLY for coupled / B2 sequential shared-spec chain tasks - never for the goals-driven N-task parallel set in 8.2.
- **Spawn-prompt context (executor stack)** - explicit, not inherited:
  - hypothesis (verbatim)
  - `goal` - the task's `hypothesis.goals[]` entry as a **condensed key-term label** (<=6 terms via the step-6 recipe: lowercase, drop stopwords + <4-char tokens; e.g. `"onboarding stuck-redirect session"` not the 16-34 word clause). One task per goal under `goals.length > 1`; the single goal under `goals.length == 1`. Do NOT restate the verbatim clause - it lives in `{session}-hypothesis.json` for step 15's per-goal list; the executor echoes this label back. The label MUST NOT enumerate file paths either - paths already live in `hypothesis.discovered_paths` and the per-task `allowed_files`; dereference via that scope, not a re-inlined list.
  - per-task scope (`allowed_files` subset)
  - **scope budget hint (E2)**: one-line `"Expected scope: <N> files, ~<K> LOC. If you exceed 2x (>2N files OR >2K LOC) OR ~35 tool calls OR you sense >~110k tokens of your own context, stop and return split-needed."` Compute K via `wc -l` on the per-task `allowed_files`. **Split-risk pre-extract clause**: when any `allowed_file` is >400 LOC (cheap `wc -l` precheck) OR holds a function at/near the ~20 cognitive-complexity warn-as-error ceiling, append `"<path> is at the file-health / complexity ceiling: extract a helper BEFORE adding field-reads or branches so the edit does not trip verify; budget +5 tool calls for the split."` to the hint.
  - step 5 lessons hits relevant to the task
  - project-context paths
  - one-line task description
  - trace path: `.claude-tmp/apex-active/{session}-traces/execute/executor-{task-id}.md`
  - **shared read-only preamble (E3)**: when a path appears in >=2 per-task `allowed_files` AND no goal names it as a write target, surface it ONCE per spawn prompt as `"Shared read-only context (do not write): <paths>"` rather than restating the contracts inside each goal. **Single-task reference-only (E3.1)**: applies WITHIN one task too - any path in this task's `allowed_files` the goal's noun set does not match is reference-only for this dispatch; surface it under the same line and let the executor Read it on demand, not the orchestrator pre-loading its content.
  - **Pre-read directive (E3.2)**: when `hypothesis.discovered_paths` are exact and small (<=5 paths AND each verified on disk at step 4), append `"Pre-read first: open every path in this task's allowed_files (<=5 files) in a single Read batch BEFORE any Grep / Glob / extra Read. Discovery already pinpointed these; re-running search adds round-trips."` to the spawn prompt. Skip when allowed_files >5 (B1 chunk-split target), when scope inherits the full main-scope (degenerate fallback), or when report-only / audit-only.
  - **Doc-text-add guard (E3.4)**: when a task's only write target is text appended/edited into an EXISTING doc (goal verbs `add` / `append` / `document` / `note` / `record` against a `*.md` path already in scope, with no `implement` / `refactor` / `rename` against any code path - distinct from B0.5, which routes plan/status docs away from executors entirely), append `"DO NOT create new files and DO NOT restructure the doc; edit the existing file in place. If the edit would breach the file-health ceiling, return split-needed rather than splitting the file yourself."` to the spawn prompt.
  - **Field-existence pre-check (E3.5)**: before a spawn prompt asserts a type field, DB column, or schema key the goal will read/write (`g.audioUrl`, `canvas_generations.niche`), grep the owning type / migration / schema to confirm it exists at dispatch time.
  - **Shared-helper pre-Read (helper_snapshot, E3.6)**: when the goal touches 2+ files where one is imported by another, OR `complexity_hint=high` with an iterative-edit shape, OR N>=2 parallel executors share a dependency file appearing in 2+ tasks' `allowed_files`, OR a single goal mechanically batch-edits N>=3 files with a shared substitution pattern (enum / symbol / key rename across many spec or fixture files), inline a pre-Read `helper_snapshot` of the shared helper body (or the batched-file bodies, one snapshot per file) in the spawn prompt.
- The executor respects file-health + scope-check PreToolUse hooks.
- The executor returns `{goal, status, notes, tool_calls_made, files_touched: ["<paths>"]}` where status is `implemented` | `already-satisfied` | `failed` | `split-needed`. `files_touched` is the actual list of repo-relative paths the executor wrote, audited against `allowed_files`. Collect per-goal returns in a session-local map for step 15's per-goal summary.
- **Post-dispatch self-report reconciliation**: before treating any `implemented` return as complete, cross-check it against the filesystem via `git status --porcelain` - confirm (a) every path in that executor's `files_touched[]` shows created/modified and (b) every file the goal statement explicitly names appears in the diff. A goal-named file absent from the diff, or a `files_touched[]` entry not in `git status`, means the self-report is false: do NOT trust `status:implemented` - re-spawn a retrace follow-up (cap 2 per goal, shared with the split-needed redispatch budget) or record the goal `failed` for step 15 when the executor annotated an explicit skip reason.
- **Cross-scope rollup before declaring complete**: scan dispatch-summary `notes` for findings naming files outside the reporter's `allowed_files` (cross-task bug discoveries surfaced by one executor in another task's domain) and queue ONE serialized follow-up to fix them (cap 1 per session). When the orchestrator inline-Edits cross-scope callers itself instead of dispatching the follow-up (mechanical signature-cascade fixes across out-of-plan files, e.g. stale callers of a renamed exported symbol), it MUST set `{session}-fix-attempts.json` to the producer-validated object `{count: N, ...}` (recording the inline-fix `kind: "cross-scope-inline"` + `files: [<paths>]` as extra context fields - the schema is an object, not an append-array) BEFORE proceeding to step 9 so the step-11 learn difficulty gate (`count >= 1`) observes the rollup and learn runs.
- **Work-produced commands**: the executor runs the setup commands the change produces (deps installs, migrations, seeders, codegen, schema / route / asset regen - open class, not closed) as part of `implemented`; only destructive / prod / credential-gated commands return `MANUAL:`-prefixed in `notes` for step 15. The orchestrator does NOT relay these as a manual checklist (see `agents/executor.md` behavior 1). **Side-effects replay log**: each state-mutating command the executor runs is appended to `.claude-tmp/apex-active/{session}-side-effects.jsonl` (one `{"cmd","ts"}` object per line). `/apex-merge` step 4.5 reads this log from every merged worktree, dedupes the union by `cmd`, and replays the unique set on main post-merge. Read-only commands (lint / typecheck / build / test) are NOT logged.
- **Dispatch self-report log (E1)**: immediately after EVERY executor Agent return (or no-spawn decision), the orchestrator MUST append ONE entry to `.claude-tmp/apex-active/{session}-traces/execute/dispatch-summary.json` (JSON array; append-and-rewrite) carrying self-reported fields AND orchestrator-measured actuals from the Agent result. Minimum entry shape - all keys MANDATORY, no exceptions for first-try-clean / economy single-dispatch / all-already-satisfied / no-spawn paths:
  ```
  {"goal": "<echoed label>", "status": "implemented|already-satisfied|failed|split-needed|no-spawn",
   "notes": "<one-line>", "tool_calls_made": <self-report>, "files_touched": ["<self-report>"],
   "tool_uses": <Agent result>, "total_tokens": <Agent result>, "duration_ms": <Agent result>,
   "git_files_touched": ["<git diff --name-only {diff_anchor} ∩ task scope>"]}
  ```
  Reflector keys its trip on the actuals + `git_files_touched`, never `tool_calls_made` / `files_touched` alone. **ASSERT post-append**: when `status != "no-spawn"`, both `tool_uses` AND `total_tokens` MUST be > 0; on a 0 / null / absent value STOP and re-extract from the Agent result (do not write a placeholder; do not advance to step 13 with it in place).
- **No-spawn sentinel (E1.1)**: when the orchestrator legitimately bypasses dispatch for a goal (e.g., economy-tier inline judgement the goal is already satisfied without an executor read pass; or a high-confidence single-Edit slice the orchestrator owns directly), append ONE sentinel entry per skipped goal to the same `dispatch-summary.json`: `{goal, status: "no-spawn", notes: "<one-line reason>", tool_calls_made: 0, files_touched: []}`. Distinct from `already-satisfied` (the executor's verdict after a read pass). The dispatch-only constraint below still forbids inline `Edit` / `Write` / `MultiEdit` / `NotebookEdit` of scope files at step 8 - the sentinel covers the read-only judgement path, not slice writes.
- **Split-needed redispatch (C1 follow-up)**: on `status: split-needed`, the orchestrator re-spawns a follow-up executor with `goal = residual_goal` and `allowed_files = residual_files`, **up to 2 follow-ups per goal (cap 2)**. Each follow-up carries **delta-only context** - the prior dispatch's `what_i_did` + the `git diff --name-only {diff_anchor}` of files it changed + the residual notes - NOT a fresh re-propagation of the full scope; the executor reads only the `residual_files` it has not touched. **Per-goal cumulative-budget guard**: track the running sum of orchestrator-recorded actual `tool_uses` and `total_tokens` across the initial dispatch + every redispatch for this goal; before each follow-up, if that sum already exceeds ~100 tool_uses OR ~300k tokens, do NOT redispatch - mark the goal `failed` for step 15 with notes `"redispatch budget exhausted; residual: <residual_goal>"`. If a follow-up still returns `split-needed` after the cap is reached, mark the goal `failed` for step 15 with notes `"split-needed x3; residual: <residual_goal>"`. Each redispatch return is also appended to dispatch-summary.json.
- On failure or split decision, the executor writes a structured trace before returning (see `agents/executor.md`).

## Dispatch-only constraint

The orchestrator MUST NOT inline `Edit` / `Write` / `MultiEdit` / `NotebookEdit` against scope files at step 8. Slice writes belong to executor subagents. Inline writes outside the scope (e.g., `.claude-tmp/` artifacts) remain allowed via the standard safety-path set.

Under `report-only` mode no executor is dispatched (step 1 contract); the orchestrator synthesizes the deliverable inline and MUST write `{session}-traces/report-only-findings.md` (classification table / ETL output) plus a `no-spawn` sentinel per goal; the declared `*-audit.md` / `*-report.md` deliverable lands within the step-1 pre-seeded scope.

## Output

- `diff_anchor` resolved in orchestrator working memory (from 8.0; propagated to every downstream agent spawn)
- Per-task trace files (only on failure or split)
- Modified scope files (touched-by-executor set; consumed by step 9 polish via `git diff` against `{diff_anchor}`)

See `agents/executor.md` for executor behavior; safety paths + hook gating enforced at the hook layer; goal-coupling vocabulary defined in 8.2 above.
